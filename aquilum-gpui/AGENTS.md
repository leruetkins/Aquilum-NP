# AGENTS.md — правила для исполнителя

Этот файл читают ИИ-агенты и люди перед любой правкой в `aquilum-gpui`.
Нарушение этих правил считается регрессией, даже если код работает.

---

## 0. Базовые поведенческие правила (общие)

Компромисс: правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных
задач — по здравому смыслу.

### 0.1. Думать до кода

Не додумывать. Не прятать неясность. Показывать развилки.

- Явно перечислить допущения; если не уверен — спросить.
- Если возможны несколько трактовок — показать их, а не выбрать молча.
- Если есть более простой путь — сказать о нём. Возражать, когда есть основания.
- Если что-то непонятно — остановиться, назвать непонятное, спросить.

### 0.2. Сначала простота

Минимум кода, решающий задачу. Ничего «на будущее».

- Никаких возможностей сверх запрошенных.
- Никаких абстракций для кода с единственным использованием.
- Никакой «гибкости» и «настраиваемости», о которой не просили.
- Никакой обработки невозможных сценариев.
- 200 строк, которые сводятся к 50, — переписать.

Вопрос себе: «Старший инженер назвал бы это переусложнённым?» Если да — упростить.

### 0.3. Хирургические правки

Трогать только то, что необходимо. Убирать только свой мусор.

- Не «улучшать» соседний код, комментарии и форматирование.
- Не рефакторить то, что не сломано.
- Держать существующий стиль, даже если сделал бы иначе.
- Заметил посторонний мёртвый код — сказать, но не удалять.
- Удалять только то, что осиротело из-за твоих правок (импорты, переменные, функции).

Проверка: каждая изменённая строка должна выводиться из задачи.

### 0.4. Цель → проверяемый критерий

Определить успех до начала работы и повторять, пока не выполнено.

- «Добавить валидацию» → «тесты на невалидный вход, затем сделать их зелёными».
- «Починить баг» → «тест, воспроизводящий баг, затем зелёный».
- «Отрефакторить X» → «тесты зелёные до и после».

Для многошаговых задач — короткий план с проверкой на каждом шаге:

```
1. [шаг] → проверка: [чем]
2. [шаг] → проверка: [чем]
```

Слабый критерий («сделать, чтобы работало») требует постоянных уточнений — это признак
плохого критерия, а не сложной задачи.

**Приоритет:** проектные правила (разделы 1–5) важнее общих при конфликте.
Переиспользование существующего компонента не считается «спекулятивной абстракцией»:
это не новый код, а отказ от копии.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний
из-за переусложнения, а уточняющие вопросы заданы до реализации, а не после ошибок.

## 1. Главное: новые компоненты не создаются

Для того, что уже существует, **запрещено** писать новый компонент.
Разрешено: переиспользовать существующий код, добавить параметр, расширить сигнатуру,
вынести общий хелпер.

Перед тем как писать новое дерево элементов, новый метод `render_*`, новую структуру
состояния, новый стиль, новую иконку или новую строку интерфейса — **сначала найди
существующее** (`grep` по имени и по `id`) и используй его. Если «не подходит» — меняй
существующее так, чтобы подошло. Не копируй.

**Что считается новым компонентом (запрещено):**

- второй метод рендера той же сущности: `render_*_v2`, `render_*_new`, `render_*_simple`,
  `render_*_in_pane`, `render_*_alt`;
- второй таб-бар: копия полосы вкладок под другим именем;
- второй редактор, второй скроллбар, второй gutter, вторые чипы кода;
- дублирующая структура состояния для того же самого (курсор, скролл, выделение, кэши);
- дублирующие `id`/классы (`leaf-tab-header-2`, `note-title-panel-alt` и т.п.);
- копия стиля или иконки вместо использования `src/theme.rs` / `src/icons.rs`.

**Признак нарушения:** в диффе появился новый `render_*`, который рисует уже нарисованное,
или новый `div`-контейнер с тем же назначением, что существующий.

## 3. Правило для задачи «сплиты и несколько панелей»

- Каждая панель получает **новый экземпляр состояния**, а не новую реализацию:
  `EditorViewState`. Одна реализация — N состояний.
- `render_central_editor` вызывается для каждой панели. Второй редактор не пишется.
- Полоса вкладок: одна реализация `render_leaf_tab_bar_strip` + параметр размещения
  (`in_titlebar`: заголовок окна / внутри панели). Вторая копия не создаётся.
- Полоса вкладок воспроизводится **целиком и в исходном порядке**: кнопка создания заметки
  **слева** от вкладок (`create_new_note_at_front` — новая вкладка встаёт в начало), вкладки,
  `×`, завершающий `+`, меню/шеврон. Отсутствующий в панели элемент — дефект, а не повод
  сделать «упрощённую» полосу.
- **Хитбокс вкладки — на всю высоту полосы**, а не по нарисованному телу (R17): события и
  `cursor_pointer` держит внешний элемент `h_full()`, а фон, рамки, hover и подпись —
  абсолютный ребёнок у нижней кромки (`bottom_0`, высота 32 px). Растянуть фон вместе с
  хитбоксом = изменить вид. То же для ведущей кнопки заметки (28 px) и `+` (26 px).
- **Текст документа существует в памяти ровно один раз** — в `DocumentBuffer` (N8, 4.5).
  Ни `OpenedNote`, ни `EditorViewState`, ни кэш неактивных листьев не держат `String` с телом
  документа. `content.clone()` / `to_string()` на теле документа в путях открытия,
  переключения, сохранения и рендера — запрещены; сохранение читает `doc.content()`.
- **Оптимизации однооконного режима сохраняются в любом режиме** (R18, N9): оконная
  виртуализация (`EditorWindow`), разреженный `LineIndex`, `f64`-индекс высот, слайс строк от
  `y≈0`, кламп offset до нарезки среза, отсутствие O(`content.len()`) в `render()`, кэши
  статистики и раскладки. Не отключать, не переписывать, не дублировать по панелям.
- Скролл, каретка, выделение, кэши раскладки живут в `EditorViewState`,
  а не в новых глобальных полях `AppView`.
- Инпут с именем файла над редактором (`#note-title-panel` / `#note-title-input`,
  `commit_title_rename_internal`) **сохраняется как есть** — тот же элемент, тот же вид,
  то же поведение. Он есть в каждой панели, а его состояние редактирования
  (`title_edit_text`, каретка, выделение, фокус) — **на вкладку**, не глобальное.
  Заменять его заголовком вкладки, крошками или «компактным» вариантом запрещено.
- **Внешний вид не меняется:** те же `id`, те же размеры, те же стили, те же отступы.
  Новое визуально — только разделители и дополнительные полосы вкладок.
- Однооконный режим должен выглядеть и работать точно как до изменений.

## 3.1. Модульная структура и размер файлов

Файл — не свалка. Новый код кладётся в модуль **по ответственности**, а не в тот
файл, который открыт в редакторе.

### Размер и ответственность
- Продовый код файла > ~800 строк — сигнал разделить по ответственности.
- Файл уже > 800 строк: новый код идёт в подмодуль, а не в этот файл.
  Исключение — правка в одну-две строки внутри уже существующей связной функции.
- Одна функция > ~500 строк: новую логику выносить в helper-модуль, а не
  наращивать функцию дальше.
- Тестовый код в лимит не входит и не живёт в продовом файле:
  `#[cfg(test)] mod tests;` + `<module>/tests.rs`. Тестовый блок > ~200 строк —
  выносить обязательно.
- Не дробить ради дробления: 2–4 тесно связанные функции без второй
  ответственности лучше оставить в одном файле.

### Куда класть новый код
1. Сначала `grep` по имени и `id`: есть ли уже модуль этой фичи?
2. Есть — добавляй туда.
3. Нет — создавай подмодуль **внутри существующего фичевого модуля**:
   `foo/bar.rs`, а не новый top-level `bar.rs`.
4. Родитель `foo.rs` остаётся фасадом: `mod bar;` +
   `pub use bar::*;` / `pub(crate) use bar::*;`. Внешние пути
   `crate::foo::Item` не меняются.
5. Приватные элементы, нужные соседнему подмодулю, получают
   `pub(super)` / `pub(crate)`. Публичный API не расширяется.
6. Общий хелпер — в `*/helpers.rs` / `*/model.rs`, только если он нужен
   двум и более подмодулям; иначе оставить рядом с использованием.

### Границы для существующих god-объектов
- Не добавляй новый метод в `AppView`, `AppState`, `SettingsView`,
  `PluginCatalogState`, `ImageEditorState`, если он относится к уже
  выделенной фиче: место — соответствующий `app_view/*.rs`,
  `state/*.rs`, `settings_view/*.rs` и т.д.
- `render_*`, `handle_*`, `save_*`, `poll_*`, `*_tab` — по фиче, а не в корень.
- Разделение модуля — это не «новый компонент» (§1): новый рендерер,
  второй таб-бар или копия состояния по-прежнему запрещены.

### Проверка
- Чистый перенос: `cargo check`, `cargo test`, `cargo clippy`; список имён
  тестов не изменился.
- В диффе — только перенос, `mod`/`use` и видимость.
- Публичные пути импорта сохранены 1-в-1.

## 4. Чек-лист перед сдачей

- [ ] Критерий проверки сформулирован заранее и выполнен (тест / скриншот-дифф / `cargo check`).
- [ ] Любая проверка приложения запуском (ручная, визуальная, `tools/gui_tester`) — только
      с `--vault <тестовый vault>` (отдельная папка, не дефолтный vault): дефолтный vault
      и его сессия (`session-state.json`, `workspace-v2.json`) не должны измениться.
- [ ] В диффе нет правок «заодно»: соседний код, форматирование и комментарии не тронуты.
- [ ] Посторонний мёртвый код замечен, но не удалён (только упомянут).
- [ ] Поиск по имени и `id` выполнен; новый элемент создан только если существующего нет.
- [ ] Нет новых `render_*` для уже нарисованной сущности.
- [ ] Нет второго таб-бара / редактора / скроллбара / gutter.
- [ ] Существующие `id` не переименованы без необходимости.
- [ ] `#note-title-panel` / `#note-title-input` на месте и не заменены другим элементом; их состояние — на вкладку.
- [ ] Хитбоксы вкладок и кнопок полосы — на всю высоту полосы, тела не растянуты.
- [ ] Нет копий тела документа (`content.clone()` / второй `LineIndex` / вторая история undo); потребление памяти не выросло.
- [ ] В однооконном режиме внешний вид не изменился (скриншот-дифф).
- [ ] Новые пользовательские строки — через i18n, не литералами в коде.
- [ ] Комментарии в коде — только по-английски.
- [ ] Новый код добавлен в модуль по ответственности, а не в самый большой
      открытый файл; файл > 800 строк не вырос.
- [ ] Тесты модуля — в `tests.rs`; inline-блок не превышает ~200 строк.
- [ ] `cargo check` проходит.

## 5. Если правило мешает

Не обходить его копией. Сначала описать в задаче или PR, почему существующий компонент
не подходит, и предложить **минимальное расширение существующего**. Копия — не аргумент.
