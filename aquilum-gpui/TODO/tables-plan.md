### Отклонения от плана господина (обоснованные)

1. **Ручной `split_table_row` не реализован — и не нужен.** `pulldown-cmark` уже отдаёт
   `Tag::TableCell` = ячейка без палок, но с пробелами (`" Имя "`), а `Text` — обрезанный контент.
   Более того, сплиттер из плана **сломан**: на `| a | b |` он выдаёт инверсный диапазон `1..0`
   и вторую ячейку `"| b"`, потому что снимает палку только у сегмента, начинающегося с нуля.
2. **Строку-разделитель не нужно «не показывать, но помнить» через ручной разбор** — парсер не
   покрывает её ни одним событием, поэтому она восстанавливается сканом одной строки после
   заголовка (`src/markdown_doc.rs:232`, `:203`).
3. **Выравнивания не парсятся из `:---`** — они приходят готовыми в `Tag::Table(vec![Alignment])`.
4. **`TableCell.row` хранит физический индекс**, логические строки — через аксессоры
   (`physical_row`/`logical_row`/`cell(row, column)`/`cell_at`). План сам предупреждал о смешении
   индексов; развёл явно, потому что иначе `cell(row, column)` возвращает ячейку разделителя.
5. **`escape_table_cell_text` не экранирует слеши безусловно** (план сам отметил это как ошибку):
   `|` экранируется только если не экранирован заранее (чётность хвоста слешей), `\r\n`/`\r`
   нормализуются до `<br>`.
6. **`make_empty_table_row(columns, line_ending)`** — второй параметр добавлен, иначе в CRLF-файле
   новая строка получит `\n` и таблица перемешается.

## 2. Что показал пробник `pulldown-cmark 0.13.4` (эмпирически, тест удалён)

- `Tag::TableHead` покрывает **только строку заголовка** (с `\n`). Тело — отдельные `Tag::TableRow`.
- `Tag::TableCell` = ячейка **без палок, с пробелами**; `Event::Text` внутри — обрезанный контент.
  **У пустой ячейки `Text` нет вовсе** → `content_range` = trim от `raw_range`, а не поиск `Text`.
- **Строка-разделитель не покрыта ни одним событием**; при отсутствии body-строк `End(Table)`
  её просто съедает.
- Короткую строку парсер **добивает** ячейкой нулевой ширины (`26..26` при тексте строки до 25),
  длинную — **обрезает** по числу столбцов заголовка.
- `End(Table)` кончается сразу после `\n` последней строки → это точка вставки новой строки.
- `| \`a|b\` | c |` **вообще не таблица**: GFM считает палки заголовка без учёта code-span, число
  ячеек расходится с разделителем, блок остаётся абзацем (тест
  `table_inline_code_pipe_is_not_a_table`). Значит делить ячейку по `|` внутри code-span не придётся.
- `\r\n`, отсутствие финального `\n`, отсутствие внешних палок — обрабатываются.

## 4. Этап 4 — раскладка и сетка

### 4.1 Новый построчный индекс таблиц: `markdown.rs::analyze_tables`

По образцу `analyze_code_blocks` (`src/markdown.rs:266`), вызывать из
`OpenedNote::rebuild_visual_cache_with_headings` (`src/state.rs:418`) рядом с ним.

```rust
pub struct TableLineState {
    pub table_id: usize,              // ключ общей раскладки
    pub physical_row: usize,          // индекс в TableModel::rows
    pub is_delimiter: bool,
    pub is_header: bool,
    pub layout: Arc<TableLayout>,     // общий для всех строк таблицы
}

pub fn analyze_tables(lines: &[&str], line_starts: &[usize]) -> Vec<Option<TableLineState>>;
```

Поиск таблиц — **по одной строке за раз** (строка, следующая за ней — разделитель): дешёвая
разметка диапазонов строк. Структуру внутри диапазона **не разбирать своей логикой** — вызвать
`parse_table_model` (§4.2).

### 4.2 Структуру брать у модели, а не парсить заново

`analyze_tables` находит только **границы** таблицы (номера строк), а затем на срезе этих строк
вызывает `parse_table_model(&content, line_starts[first], &range, &events)` (`src/markdown_doc.rs:260`).
Один `Parser::new_ext` на таблицу, только при `rebuild_visual_cache` — **не в кадре**.

Так проверенная модель остаётся единственным описанием структуры, а рендер получает построчный вид
(строка → физическая строка модели → ячейки).

### 4.3 `TableLayout` и ширины столбцов

```rust
pub struct TableLayout {
    pub column_widths: Vec<f32>,
    pub row_height: f32,
}
```

**Инвариант проекта (из `MEMORY.md`): модель «столбец × `char_w`» запрещена** — источник истины
шейпленный layout (эмодзи до 21.6 px). Значит ширины столбцов измерять шейпером
(`WindowTextSystem`), а не `число_символов × средняя_ширина`, как предлагал план.

Порядок: ширина столбца = max по измеренным ширинам его ячеек (заголовок + тело), затем
нормировка под доступную ширину редактора. Считать **один раз** на (таблица, доступная ширина,
`scale_factor`) и кешировать — в существующем `LayoutCache` (`src/markdown_doc.rs:1391`,
ключ `LayoutKey` — `src/markdown_doc.rs:1379`) или отдельным кешем. **Пересчёт при движении мыши
запрещён** — это прямо записано и в плане господина, и в `MEMORY-perf.md`.

### 4.4 Отрисовка: ветка в `render_live_styled_row`

`src/views/app_view.rs:6408` — новый `match`-рукав `LineKind::TableRow { .. }`: `flex_row` из
`column_count` ячеек фиксированной ширины из `TableLayout`. Текст ячейки рисовать через
существующий `render_syntax_spans` (`src/views/app_view.rs:6000`), чтобы внутри ячейки работали
жирный/курсив/code-chip. Сетка — рамки/фоны; заголовок — своим фоном и весом.

### 4.5 Строка-разделитель: **развилка, выбрать до начала работ**

`build_visual_rows` (`src/markdown.rs:826`) сейчас даёт ровно одну визуальную строку на каждую
строку текста, и на этом 1:1 держатся `find_visual_row_for_cursor` (`src/markdown.rs:848`),
выделение и переходы. Варианты:

- **A. Ноль высоты.** `VisualRow` выпускается, но высота 0 (`VisualRowHeightIndex::from_rows`,
  `src/markdown.rs:923`), элемент не рисуется, слушателя клика нет. 1:1 сохраняется, строка
  невидима и некликабельна. Требует: пропускать её в `move_cursor_up_visual`/`down_visual`
  (`src/views/app_view.rs:755,799`) и не давать выделению дать нулевую высоту.
  **Рекомендую — лучший визуальный результат при сохранении индексов.**
- **B. Не выпускать `VisualRow` вовсе.** Чище концептуально, но ломает 1:1: правки нужны в
  `find_visual_row_for_cursor`, в выделении и в переходах. Больше риска.
- **C. Рисовать как линию сетки** (прецедент — `HorizontalRule`/`CodeFence`:
  `src/markdown.rs:1460` рисуют не то, что в тексте, сохраняя геометрию сырой строки). Ноль риска
  для индексов, но 24 px вертикального зазора на месте разделителя — визуально хуже.

### 4.6 Зеркало геометрии — обязательное условие

`row_painted_text` (`src/markdown.rs:1374`) **обязан** получить рукав для `LineKind::TableRow`, иначе
каретка, выделение и клик разъедутся с тем, что нарисовано. Для таблицы одного `PaintedRow`
недостаточно (там один текст и один `line_chars`): нужна структура вида
`Vec<{ painted: PaintedRow, x: f32, width: f32 }>`, и `shape_row`
(`src/views/app_view.rs:6347`) — парный `shape_table_row`, возвращающий по одному `RowShapedLayout`
на ячейку со своими x. `RowShapedLayout` переиспользуется как есть.

## 5. Этап 5 — активная ячейка и каретка

- Позиция курсора **остаётся байтовым смещением** (`cursor_offset`); пара `(row, column)` —
  вычисляемое представление. План господина прав, менять это нельзя.
- Активная ячейка: `TableModel::cell_at_directional(pos, moving_right)` (`src/markdown_doc.rs:471`).
  Смещение → модель: строка визуальной раскладки знает `physical_row`, позиция в строке → колонка.
- Клик: `on_mouse_down` (`src/views/app_view.rs:5332`) сейчас идёт через
  `row_layout_down.column_for_x(click_x - text_start_x)` → `line_char_for_column`. Для таблицы
  сначала выбрать ячейку по x (`TableLayout::column_widths`), затем `column_for_x` **внутри ячейки**.
- Каретка в неактивной ячейке — не рисовать; активная ячейка получает рамку/фон, каретка остаётся
  на настоящей позиции в тексте.
- Правила границ (план господина, §7): позиция внутри содержимого ячейки или на её границе →
  эта ячейка; позиция на `|` → ближайшая по направлению движения; в строке-разделителе → ничья
  ячейка (уже так: разделитель не входит в `data_rows`, `cell_at` вернёт `None`).
- `is_active_editor_line` (`src/views/app_view.rs:1813`) для строки таблицы оставить истинным,
  чтобы редактируемая ячейка показывала сырой текст.

### Тесты этапа 5
- Клик по каждому столбцу попадает в свою ячейку (включая крайние x и ячейки нулевой ширины).
- Клик по `|` и по паддингу — в ожидаемую ячейку по направлению.
- Каретка в ячейке — x совпадает с шейпленным глифом (не с `column × char_w`).

## 6. Этап 6 — правка ячейки

Точка врезки: `AppView::handle_key` (`src/views/app_view.rs:2658`), диспетчер клавиш —
`:2867-2875` (`"tab"` сейчас `insert_text("    ")`, `"backspace"`, `"delete"`, стрелки). Ветку
таблицы ставить **до** общих рукавов, только когда курсор в ячейке.

**Все изменения текста — через существующие точки `state.rs`, тогда undo/redo бесплатны:**
`snapshot_undo` (`src/state.rs:467`), `insert_text` (`:680`), `replace_selection` (`:548`),
`delete_backwards` (`:721`), `delete_forwards` (`:750`). `insert_text` и `replace_selection` сами
зовут `snapshot_undo` — **одна транзакция на вызов**, поэтому многоячеечную вставку (TSV) делать
одним вызовом, а не N.

| Клавиша | Действие |
| :--- | :--- |
| `Tab` / `Shift+Tab` | `next_cell(pos, backwards)` (`src/markdown_doc.rs:544`); `None` → §7 |
| `Enter` | ячейка ниже в том же столбце (курсор остаётся позицией в тексте) |
| `Shift+Enter` | `escape_table_cell_text` → `<br>` в текущей ячейке |
| `Backspace` в начале ячейки | **не** удалять разделитель (не выходить за `content_range.start`) |
| `Delete` в конце ячейки | **не** удалять разделитель |
| ввод `\|` | `escape_table_cell_text` (`src/markdown_doc.rs:602`) → `\|` |

`replace_cell_text` (`src/markdown_doc.rs:576`) — замена только `content_range`, паддинг не трогает.

### Тесты этапа 6
- Правка ячейки не меняет соседние ячейки (сравнение среза до/после).
- `Backspace`/`Delete` на границе ячейки не удаляют `|`.
- Одна операция = одна запись undo (проверить длину `undo_stack`).

## 7. Этап 7 — структурные операции

- Новая строка: `make_empty_table_row(column_count, line_ending)` (`src/markdown_doc.rs:585`)
  в `row_insert_offset()` (`:569`) — это `End(Table)`, то есть сразу после `\n` последней строки;
  следующий абзац не затрагивается (закреплено тестом `table_row_insert_offset_lands_after_the_last_row`).
- `Tab` в последней ячейке последней строки данных → добавить строку и встать в её первую ячейку.
  `Tab` в ячейке заголовка → перейти в первую ячейку данных (не создавать строку).
- Вставка TSV: табуляции → столбцы, переводы строк → строки, собрать весь блок строк и вставить
  **одним** `insert_text` (одна транзакция undo), курсор — в последнюю вставленную ячейку.
- Локальный пересчёт (только затронутый блок) — **не** в первой версии: сначала полный
  `rebuild_visual_cache`, как сейчас. Прямая замена диапазонов в `TableModel` руками запрещена —
  смещения всех последующих ячеек меняются.

### Тесты этапа 7
- Добавление строки не затрагивает следующий абзац.
- Вставка TSV 3×4 отменяется одной операцией undo.
- После добавления строки `TableModel` даёт `data_row_count` + 1 и пустые ячейки.

## 8. Чего не делать (подтверждает план господина)

- Не создавать отдельный буфер текста на ячейку и не хранить копии содержимого ячеек: источник —
  только `source`.
- Не заменять Markdown-парсер самописным разбором всего документа.
- Не пересчитывать геометрию таблицы при движении мыши.
- Не оптимизировать локальный пересчёт до того, как диапазоны и структурные операции покрыты
  тестами.
- Не переиспользовать `MarkdownDocument` для рендера (§1): он пересобирается только на правку
  и его не читает UI.

## 9. Инварианты проекта, которые нельзя нарушить (из `MEMORY.md` / `MEMORY-perf.md`)

- Геометрия строки — только шейпленный layout, модель «столбец × `char_w`» запрещена.
- Каретка и любой прямоугольник выделения снапаются на сетку устройства (`snap::snap_x` /
  `snapped_span`).
- Кламп смещения — **до** нарезки среза (для таблиц критично: срез строк и высоты идут врозь).
- В `render()` нет работы O(`content.len()`); всё производное от текста — через кеш.
- Комментарии в коде — только по-английски.
