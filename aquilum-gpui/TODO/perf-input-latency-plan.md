# План: инпут-латентность редактора (Delete, удержание клавиши, сплиты)

**Статус: внедрено (2026-10-20), cargo test 410 зелёных.** Пункт 3 оказался no-op — см. ниже.

Симптомы (подтверждены чтением кода):

1. Первый Backspace/Delete после открытия большой заметки «задумывается» ~2 с (в debug),
   дальнейшие удаления мгновенные.
2. Удержание буквы: 13–15% GPU и ~5% CPU (≈40% одного ядра на 8 ядер) — и это без word wrap,
   так что пересчёт переносов ни при чём.
3. Одна и та же заметка в двух панелях сплита умножает стоимость правки на число панелей.

«Мультиокна» в смысле отдельных OS-окон нет: один `open_window` (`src/main.rs:61`),
«Move to new window» — заглушка, пишет только статус (`src/views/tab_context_menu.rs:529-538`).
Речь о сплитах внутри одного окна.

## Причины (проверено по коду)

| # | Причина | Место |
| :- | :--- | :--- |
| 1 | Backspace/Delete вызывает `doc.ensure_table_index()` **до** проверки выделения; у заметки >3000 строк индекс после открытия не полный (`fully_scanned=false`, `table.rs:155,248`), поэтому первый вызов = полный `scan_rope` по всему документу. Повторные — мгновенны. То же в Ctrl+C | `views/app_view.rs:4427`, `:3973`; `document_buffer.rs:165-172` |
| 2 | После быстрого инкрементального `update_window_line_after_edit` безусловно ставится `visual_cache_dirty = true` → на каждый символ полный ребилд окна `2*MARGIN_LINES+1 = 6001` строк | `workspace/view_state.rs:536,534,901-917`; `editor_window.rs:35,327` |
| 3 | На каждый символ `update_window_line_after_edit` пересканирует весь диапазон окна таблиц (`ensure_table_index_for_window` по `[start_line, end_line]`); после `apply_edit` покрыт только абзац → перескан ~6200 строк. Второй такой вызов — в обработчике клавиш | `workspace/view_state.rs:547`; `views/app_view.rs:4133` |
| 4 | Settle-кадры усадки layout запрашиваются при каждом изменении scroll-инпутов, а высота меняется с каждым символом → непрерывный репейнт при key-repeat | `views/app_view.rs:8506-8515`; выставление счётчика `:986, :4989, :5068, :5095` |
| 5 | Undo-склейка Backspace — prepend: `insert_str(0, …)` сдвигает весь накопленный буфер, серия из n Backspace = O(n²) копирования. Forward delete уже `push_str` (амортизированный O(1)). Склейка рвётся на `\n` (`:690`), так что деградация — на длинных строках и при стирании мегабайтов одной серией | `document_buffer.rs:688-706` |
| 6 | Внешние view (сплит с той же заметкой): правка внутри их окна сбрасывает окно целиком (`EditorWindow::default()` + dirty) → полный ребилд в `ensure_inactive_views_built` на следующем кадре. Правки вне окна — только сдвиг above/below, это уже дёшево | `workspace/view_state.rs:1032-1057`; `views/app_view.rs:4796-4882` |

Вторично: `poll_fs_changes` каждые 150 мс делает `path.exists()` для каждой открытой заметки
на UI-потоке — двухсекундный фриз не объясняет, но микрофризы добавлять может, особенно на
сетевых дисках (`src/main.rs:141,145`; `src/state.rs:1619`).

## Шаги

1. ✅ **Delete/Backspace без полного скана.** В обработчике сначала `selection_range`; индекс
   таблиц запрашивать только при наличии выделения и через
   `ensure_table_index_for_window(start_line, end_line)`. То же для Ctrl+C (`app_view.rs:3973`).
2. ✅ **Не грязить весь кеш после успешного инкрементального апдейта** (`view_state.rs:536`).
   Реализация оказалась строже исходной идеи: инкрементальный путь принимается только для
   **строк без `|`** (guard в `update_window_line_after_edit`) — таблицы и любые трубы
   консервативно уходят в полный ребилд. `update_single_line` теперь: отказывается от строки
   фенса (её state переопределяет все следующие строки окна), пересчитывает высоты только
   заменённых строк через новый `VisualRowHeightIndex::replace_rows` (вместо полного
   пересчёта на 6001 строку), а настройки заголовков кешируются в view (`headings_cache`,
   обновляется каждым полным ребилдом и `ensure_inactive_views_built`). Безусловный
   `visual_cache_dirty` из `dispatch_edit_event` для исходной view тоже снят — view-методы
   управляют своей инвалидацией сами.
3. ✅ **Пункт оказался no-op.** `TableIndex::apply_edit` не сужает `covered_range`, а расширяет
   (`min`/`max`), а `scan_window` при покрытии выходит сразу — перескана окна на каждый символ
   не было. Зафиксировано тестом `scan_window_is_noop_while_edit_stays_inside_covered_range`
   (`table.rs`). Отметка «сканирует до ~6200 строк» в исходном анализе была неверна.
4. ✅ **Settle-кадры с порогом.** RAF-бёрст запрашивается только при смене высоты вьюпорта
   (resize — явного хука нет) или скачке `max_scroll` больше 25% высоты вьюпорта; посимвольные
   дельты больше не просят кадр. `last_scroll_inputs` обновляется всегда, чтобы дельта
   оставалась покадровой.
5. ~~Отпадает при посимвольном undo~~ (реализовано ранее).
6. ✅ **Сплиты:** внешняя view при same-line правке без труб обновляет строку in-place через
   тот же `update_window_line_after_edit`; полный ребилд только при смене числа строк, трубах
   или фенсах. Правки вне окна — как раньше, дёшево (сдвиг above/below).

## Ожидаемый результат

- Удержание буквы: одна вставка в rope + инкрементальный `apply_edit` (абзац) + апдейт одной
  строки + один репейнт; без полных проходов по документу и по окну.
- Backspace/Delete: без фриза на первом удалении; стирание мегабайтов одной серией — O(n)
  (после п.5).
- Сплиты: одна заметка в N панелях — один инкрементальный апдейт + N дешёвых (после п.6).

Замерять в release: debug-сборка в разы медленнее и часть фризов даёт сама.

**Замер на Ryzen 7 7700 (2026-10-21, debug):** простой ~1% GPU; удержание клавиши
было 10–15% GPU (очень большой md) / 10–12% (пустая), стало **7–8% / 7%**. FPS-монитор:
в простое 2–4 рендера/с (только мигание), при удержании ровно ~30 рендеров/с = один кадр
на символ (архитектурный минимум при пофреймовом present). shape=1674/с на большой заметке
≈ 31 кадр × ~54 видимых строки — подтверждено отсутствие кеша шейпинга (§3 perf-plan,
единственный оставшийся рычаг, фаза 2). GPU почти не зависит от размера документа
(8% против 7%) — цена кадра, а не документа. Бенчмарк пайплайна ввода
(`benchmark_key_repeat_throughput`): 0.003–0.025 мс/символ (40–290 тыс симв/с) — логика
ввода не является узким местом с запасом ×1000.

**П.4 уточнён (2026-10-21, «каретка рывками, выделение запаздывает»):** один кадр на
символ при key-repeat — это ~30 fps, и шаг каретки в 33 мс глаз видит как рывки; без
усадочных кадров reveal-скролл и render-кламп сходятся через кадр, и выделение выглядит
отстающим. Часть прежних 13–15% GPU была ценой плавности набора. Фикс: текстовая правка
или сдвиг курсора/выделения в `handle_key` ставит `layout_settle_frames = 1` (не 3, как
раньше) — при наборе ~60 fps, GPU вернёт пару процентов, пересборка окна на символ
не возвращается.

**П.4 пересмотрен (2026-10-21, вечер, после кеша шейпинга строк).** Кеш строк заработал,
но сначала счётчик врал: `shape_calls` инкрементировался в рендер-цикле
(`visible_range.len()` — строк на кадр), поэтому «shape=3192» не отражал кеш. Счётчик
перенесён внутрь `shape_row`/`shape_table_row` (реальные укладки), добавлен
`shape_cache_hits`. Замер с работающим кешем: shape 3192 → **600–720/с** (×5), хиты
~3200/с — шейпинг больше не узкое место. GPU при этом не сдвинулся (18–20%) → GPU
масштабируется **числом кадров**, а не стоимостью кадра: 57–60 рендеров/с при ~30
симв/с = два кадра на символ. До сбоя драйвера было ровно ~30 рендеров/с и 7–8% GPU
(см. замер выше); удвоение дал settle-кадр из П.4, введённый по отчётам, которые
потом объяснились сбоем драйвера видеокарты. Итог: settle-кадр ставится только когда
правка реально сдвинула скролл (reveal в `scroll_cursor_into_view` записал сдвиг
> 0.5 px) — набор в середине вьюпорта рисует один кадр на символ, набор у края
вьюпорта и прокручивающие нажатия по-прежнему получают усадочный кадр. Ожидание:
~30 рендеров/с и ~8% GPU при удержании клавиши; если каретка снова покажется
ступенчатой на 30 fps — это осознанный компромисс из первого замера (плавность
за счёт GPU).

**Итог кампании (2026-10-21, финальный замер).** После settle-правки: 30–31 рендер/с
(один кадр на символ), shape 420–605/с, shape_hits ~1450–1700/с. GPU при удержании:
**~9%** (большой md-файл), **~10%** (632 МБ файл без markdown). Это уровень первого
замера (7–8%) с точностью до шума debug-сборки. Дальнейшее снижение GPU упирается в
цену одного кадра: gpui без damage-регионов перекрашивает всё окно целиком на каждый
present, и при одном кадре на символ быстрее уже некуда (простой ~1% подтверждает,
что это цена именно набора). Следующий рычаг — damage-регионы/частичный present в
vendored gpui (большая работа, фаза 2, отдельное решение). Кеш шейпинга строк
(§3 perf-plan-aquilum) при этом остаётся в запасе: CPU на кадр упал ×5 — полезно на
слабых CPU и при росте числа кадров (сглаженный скролл, драги).

## Риски / инварианты

- П.2 не должен сломать инвалидацию при смене markdown-kind строки и при раскрытии/скрытии
  таблиц — там `visual_cache_dirty` легитимен (`view_state.rs:883,896`).
- П.1 не должен сломать определение «удаление внутри таблицы»: без полного индекса
  `tables.at(line)` вне окна вернёт None — скан должен покрывать диапазон выделения.
- Настоящее второе окно (если появится): с общим `AppState` упирается в п.6, с независимыми
  буферами — в конфликты сохранения (сейчас разные окна связаны только опросом ФС раз в 150 мс).
