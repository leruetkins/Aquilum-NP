## 1. Поиск по сайдбару — самое крупное (P1)

### 1.1 Что не так

`run_sidebar_search` на каждый символ запроса: собирает до 2000 путей из дерева, затем
`search_goto_files_opts` **синхронно читает каждый файл** (`goto_search.rs:657`) — даже для
операторов `file:`/`path:`, которым контент не нужен. Хранилище на 2000 файлов среднего размера
= десятки МБ чтения с диска на нажатие клавиши, всё на UI-потоке. Плюс аллокации fold-копий.

### 1.2 Шаги

1. Точечная победа без потоков: читать контент **только тем операторам, которым он нужен**
   (`Any` — да, `File`/`Path` — нет, `Tag`/`Line`/`Section` — да). Один if на месте чтения.
2. Кеш содержимого между нажатиями: `HashMap<PathBuf, (mtime, Arc<String>)>`, инвалидация по
   `metadata().modified()`. Существующие записи не перечитываются при наборе запроса.
3. Полный вариант: перенос `search_goto_files_opts` в `background_executor` с epoch-гвардом
   (побеждает последний запрос) и дебаунсом ~150 мс; на UI-потоке только применение результатов.

Критерий: набор запроса в хранилище на 2000 файлов не даёт пропусков кадров
(замер `perf.rs`-счётчиком), `cargo test` зелёный (существующие тесты поиска не меняются).

## 2. save_session_state — два синхронных JSON на UI-потоке (P1)

### 2.1 Что не так

Каждый автосейв (а это каждая пауза набора ≥ debounce, т.е. десятки раз за сессию) сериализует
в pretty-JSON всю сессию — включая безгранично растущий `note_states` — и пишет два файла
синхронно на UI-потоке. На большом `session-state.json` это видимый стоп кадра сразу после
паузы в наборе — совпадает с субъективным «подтормаживает после остановки печати».

### 2.2 Шаги

1. Разделить: мутация `self.session`/`note_states` (дёшево, синхронно) и сериализация+запись
   (тяжело) — запись уходит в `background_executor` через snapshot полей.
2. Тротлинг: не писать чаще раза в N секунд и только при реальном изменении (флаг dirty у
   session, сбрасываемый после успешной записи).
3. `export_workspace_session_v2` строится на UI-потоке (это O(вкладок), дёшево) — фону
   отдаётся только сериализация.

Критерий: после остановки набора UI-поток не выполняет файловых записей — проверяется
инструментально (счётчик вызовов `fs::write` в UI-потоке через точку монтирования), тесты
сессии зелёные.

## 3. Опрос ФС → заменить на событийный watcher по образцу оригинального Aquilum (P2)

**Развёрнут в отдельном плане: `fs-watcher-plan.md`** — там же полный протокол внешних правок
(pull: stamp → hash → перечитка; push: expected_hash → конфликтная копия вместо затирания),
инвариант размещения для мультипанели/мультиокна и пошаговая реализация. Здесь — кратко.

### 3.1 Что не так сегодня

Каждые 150 мс: клонирование всех открытых путей + `path.exists()` — мелочь на локальном SSD,
но таймер крутится всегда и мешает настоящему простою; на сетевых дисках `exists()` — блокирующий
сетевой вызов на UI-потоке. И главное: опрос порождает **только** `Deleted` — ветки
`Modified`/`Renamed` в обработчике мёртвы, внешние изменения открытого файла не подхватываются.

Назначение текущего опроса — обнаружение удаления/переименования файлов другой программой,
чтобы вкладки и проводник оставались честными. Отслеживать изменения надо, но не так.

### 3.2 Как сделано в оригинальном Aquilum (Aquilum/aquilum-app, проверено по коду)

- Крейт **`notify` 8.2.0** (`core/Cargo.toml:20`), `recommended_watcher`: на Windows это
  `ReadDirectoryChangesW` — события приходят от ОС, на UI-потоке нет ни одного таймера и ни
  одного `exists()`.
- Наблюдение за **всим корнем хранилища рекурсивно**, запускается один раз на фоновом потоке
  (`native/src/app/panel/mod.rs:19-28`, `start_index`).
- Отдельный поток `aquilum-fs-watch` (`core/src/files/watcher/mod.rs:74-77`): notify-колбэк
  шлёт события в mpsc-канал, поток-доставщик вызывает `coalesce` и передаёт пакет в sink.
- **`coalesce` — окно 80 мс** (`batch.rs:6-44`): события схлопываются в один батч, пути
  дедуплицируются, побеждает «глубокий» scope. Одна групповая правка (например, наш же
  атомарный сейв tmp→rename) даёт один пакет, а не бурю.
- **`classify`** (`classify.rs`): `Access` игнорируется; только markdown/текст считаются
  заметками; `Create/Remove/Modify(Name)` → структурные, `Modify(Data)` → контентные; удаление
  папки и ошибка вотчера → полный Rescan; `RenameMode::Both` (атомарная запись `.tmp` →
  `заметка.md`) превращается в одно событие заметки без рескана; скрытые пути фильтруются.
- Sink → `CoreEvent` (`app_core.rs:85-150`): Content → `ContentChanged`, структурные →
  `WorkspaceChanged`, рескан → `WorkspaceRescanned`. Внутри `ingest_watch` вызывается
  `documents.reconcile_paths`, который порождает `NotesRelocated` со списком удалённых —
  UI по нему закрывает вкладки (`close_missing_tabs`, `native/src/app/core_events.rs:64-75`).
- UI-поток **не опрашивает ФС вообще**: раз в кадр он неблокирующе выгружает канал событий
  (`drain_events`), по `ContentChanged` открытой заметки перечитывает её с диска
  (`note.reload()`, `core_events.rs:85-90`) — т.е. внешние изменения открытого файла
  оригинал подхватывает, а мы нет.
- Список файлов для поиска индексируется инкрементально из тех же событий
  (`search.ingest_watch`), а не обходом каталога.

### 3.4 Внешняя правка открытого файла в оригинале — двусторонний протокол (проверено по коду)

**Сторона чтения** (`native/src/note/mod.rs:136-152`, `Note::reload`):
1. Если есть несохранённые правки (pending debounce) или запись в полёте (queued) — перечитать
   **отказ**: свои правки никогда не затираются внешней версией (`reload_ignores_own_write...`
   тест на это).
2. Двухступенчатая дешёвая проверка: сначала **stamp** = (размер файла, mtime) — не изменился,
   значит и нечего перечитывать; затем **blake3-хеш файла** — совпал с запомненным хешем диска
   (например, другая программа перезаписала то же самое), обновить stamp и выйти без перечитки.
3. Только после обоих промахов — чтение файла, adopted как новая disk-версия, сброс dirty-регионов,
   текст отдаётся в редактор (`set_text`, `core_events.rs:85-90`).

**Сторона записи — конфликтная копия** (`native/src/note/save.rs:30-54`):
- Каждый сейв несёт `expected_hash` — хеш содержимого, на котором основан буфер.
- `gate::save` сравнивает с фактическим состоянием диска; расхождение (пока мы редактировали,
  файл перезаписали извне) → `Conflict` — **не** затирание, а `preserve_copy`: версия
  пользователя сохраняется в отдельный конфликтный файл, буфер принимает версию с диска
  (`Outcome::Copied`), статус-бар показывает локализованное `editor.conflictCopy`.
- Подхват в UI: в покадровом `tick` (`lifecycle.rs:23-27`) `take_replaced` отдаёт дисковый
  текст, редактор заменяется, показывается статус.
- Порядок собственных фоновых сейвов — счётчик seq/after (`save.rs:24-37`, `mod.rs:81-87`):
  задача записи применяется, только если на диске не появилось более новой собственной записи.

**Наше текущее состояние по этому протоколу** (для сравнения):
- Pull-сторона есть наполовину: `handle_file_modified` (`state.rs:1559-1590`) при dirty
  показывает статус и не перечитывает (как у них), при чистом — перечитывает целиком без
  stamp/hash-проверок. Но ветка мёртвая — опрос не порождает `Modified`.
- Push-стороны **нет вовсе**: `save_document`/`flush_document_now` пишут через
  `safe_write_rope` без проверки ожидаемого хеша — при сценарии «оба редактировали» наш
  автосейв молча затирает внешние правки (оригинал в этом случае делает конфликтную копию).
  Это единственный в протоколе пункт с риском потери данных, не просто перф.

### 3.3 Шаги (переносим приёмы, не код; лицензия AGPL на ideи не распространяется, но код не копируем)

1. Завязать `notify` (`recommended_watcher`) на корень хранилища рекурсивно; фоновый поток
   с coalesce-окном ~80 мс и дедупликацией путей.
2. Классификация по упрощённой схеме: Deleted (файл/папка), Renamed { old, new },
   Modified (только открытые документы интересуют), Rescan при ошибке вотчера и удалении папки.
3. Доставка в UI: неблокирующая выгрузка канала из `poll_fs_changes`-заменителя, вызванного
   раз в кадр (или из таймера с редким интервалом) — без системных вызовов в тике.
4. `Deleted` → существующий `handle_file_deleted` (с сохранением debounce-логики атомарного
   сейва: переименование tmp→целевой не должно выглядеть как удаление — в классификаторе
   это уже покрыто парами Rename). `Renamed` → оживить существующий `handle_file_renamed`.
   `Modified` → оживить `handle_file_modified` по протоколу §3.4: не перечитывать при
   несохранённых правках, stamp (len+mtime) → blake3-хеш → перечитка; а при сохранении
   собственного dirty-документа с расходящимся хешем диска — **конфликтная копия** вместо
   молчаливого затирания (риск потери данных закрыть обязательно).
5. Fallback: если `recommended_watcher` недоступен (сетевой диск без поддержки) —
   `notify::poller`-вариант с редким интервалом (секунды, не 150 мс), только пока watcher не поднялся.
6. Опросный таймер 150 мс удаляется целиком после переключения.

Критерий: в простое с открытой заметкой UI-поток не делает системных вызовов ФС вовсе;
удаление/переименование/внешнее изменение файла сторонней программой отражается во вкладках,
проводнике и открытой заметке; наш собственный атомарный сейв не порождает ложных событий
(тест по образцу `an_atomic_write_rename_stays_a_note_event_and_does_not_trigger_a_rescan`).

## 4. publish_snapshot (P2)

При каждом сохранении клонируется весь список файлов хранилища. Заменить кеш на
`Arc<Vec<FileInfo>>` и хранить `Arc` в снапшоте напрямую (`Snapshot.files` уже `Arc<[FileInfo]>` —
превращение без копирования при смене типа поля). Мелочь, делается попутно с п.2.

## 5. reload_file_tree на фоне (P3)

Полный обход хранилища при обработке удаления — редкое событие, но на большом хранилище это
стоп кадра. `build_tree` уходит в фон, готовое дерево подменяется по завершении. Дешёвый вариант
по схеме уже существующего `flush_document_now` (spawn → update).

## 6. Моргание каретки (P3, уже запланировано)

Уведомление корня каждые 530 мс — это основной расход GPU/CPU **в простое**. Не дублируется:
это §1 плана `perf-plan-aquilum.md` (каретка в свой `Entity` + `.cached` на тяжёлых соседях).

## Что сознательно не делаем

- Изменений UI нет: правки только в моменте запуска поиска/сейва и в фоне; рендер и внешний вид не трогаем (AGENTS.md).
- Не переводим весь ввод на async ради async: пункт 1 решается сначала дешёвыми шагами 1–2.
- Не переносим `save_document` (синхронная запись по Ctrl+S/закрытию) в фон в этом плане — это отдельные UX-решения (что показывать, пока файл не записан).
- `log_fps_tick` — debug-only, не трогаем.
