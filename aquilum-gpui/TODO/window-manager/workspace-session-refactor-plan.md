# План рефакторинга: единое состояние вкладок (Workspace)

Цель: убрать «split-brain» (поля AppView + OpenedNote + EditorViewState + DocumentBuffer), чтобы данные одной вкладки не попадали в другую, а один файл можно было открыть в нескольких сплитах.

Целевая схема (3 слоя):
1. `DocumentRegistry` — владелец текста, line_index, undo/redo, path, title.
2. `TabSessionStore` — `TabSession`: doc_id, курсор, вьюпорт, `Option<TitleInput>`; плюс отдельный производный `ViewCache`.
3. `WorkspaceLayout` — дерево сплитов, `LeafState { tabs, active, bounds }`.

Фасад `Workspace` координирует слои. Закрытие вкладки двухфазное: `request_close` → эффекты (`CommitTitle`, `FlushDoc`) → `finish_close`.

Правила работы на всех этапах:
- Каждый шаг заканчивается рабочей сборкой и отдельным коммитом. Состояния «ничего не работает» быть не должно.
- Любое изменение текста идёт только через `DocumentRegistry::apply_edit` (в т.ч. внешние изменения с диска, `origin: None`).
- Не меняйте поведение и рефакторинг в одном коммите.

## Этап 1a. Убрать `OpenedNote`
Самый рискованный этап. Пока текст «переезжает» между `DocumentBuffer` и `OpenedNote`, один файл не может быть открыт в двух вкладках.

- [ ] `OpenedNote::record_change`, `undo`, `redo` превращаются в тонкие обёртки над `DocumentRegistry::apply_edit/undo/redo`. Интерфейс для вызывающего кода не меняется.
- [ ] Обёртки возвращают `EditEvent`; `pending_edits` пока остаётся и наполняется из него (параллельно).

Шаг 2. Читать из реестра
- [ ] Весь доступ к `content`, `line_index`, `code_checkpoints`, `version`, `is_dirty` в UI переводится на `DocumentBuffer`.
- [ ] Привести к одному типу `stats_cache`: сейчас `(u64, TextStats)` в `DocumentBuffer` и `(u64, usize, TextStats)` в `OpenedNote`. Остаётся вариант документа; выяснить, зачем нужен третий элемент (`usize`), и перенести его смысл (вероятно, в ключ).
- [ ] Курсор и выделение читаются из сессии вкладки, а не из `OpenedNote`.

Шаг 3. Убрать чек-аут
- [ ] Удалить `stash_from_note` и выдачу владения при активации вкладки.
- [ ] Переключение вкладки больше не двигает текст, только меняет активный указатель.

Шаг 4. Рассылка событий и удаление
- [ ] `EditEvent` рассылается через `TabSessionStore::apply_edit_event` сразу при правке.
- [ ] Удалить `pending_edits`, `NoteEditEvent`, `sync_views_for_active_note` (по аудиту они используются в одном месте).
- [ ] Удалить `OpenedNote`.

## Ручная проверка (чек-лист перед закрытием каждого этапа)
1. Открыть один файл в двух сплитах, печатать выше курсора второго: курсор и видимый текст второго не прыгают.
2. Undo в одном сплите после правки в другом: текст откатился, курсоры корректны.
3. Редактировать заголовок и закрыть вкладку: имя применилось; при коллизии имени вкладка осталась, ввод цел.
4. Закрыть вкладку в середине ряда: соседи сохранили заголовок, скролл, курсор.
5. Двигать сплиттер: скроллбар верхнего окна не «улетает».
6. Переименовать файл: все вкладки показывают новое имя.
7. Удалить файл с открытыми вкладками: вкладки закрыты, ошибок нет.

## Открытые вопросы (зафиксированные решения)
- **Что означает третий элемент (`usize`) в `OpenedNote.stats_cache`?**
  Это была длина строки `content.len()`, которая проверялась вместе с версией (`v == self.version && l == len`). Поскольку `version` увеличивается при каждой правке, проверка `v == self.version` из `DocumentBuffer` исчерпывающа; `usize` убирается.
- **Куда уходят кэши координат курсора и вьюпорта из `OpenedNote` (`view_shell_*`)?**
  Поскольку они вычисляются из раскладки конкретного окна/панели, они переходят в `ViewCache` вкладки.
- **Нужен ли общий undo между сплитами одного документа?**
  Да, строго общий на документ (как в VS Code / Zed). При общем буфере текста раздельный стек undo приводил бы к рассинхронизации смещений правок.
- **Поведение курсора, когда другой сплит удаляет текст вокруг него:**
  Сдвиг в `at` (в начало диапазона удаления), что уже заложено в `transform_offset` и является отраслевым стандартом.
