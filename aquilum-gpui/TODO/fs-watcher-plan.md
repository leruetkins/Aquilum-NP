# План: событийное отслеживание ФС (notify) по образцу оригинального Aquilum

**Статус: внедрено 2026-10-20, cargo test 433 зелёных.** Шаги 1–6, 8–9 выполнены.
Отложено: §7-фон для reload_file_tree (см. perf-microfreezes-plan §5); трёхстороннее слияние — фаза 2.

Отступления от плана по ходу внедрения (все — в безопасную сторону):
- Доставка: notify-watcher владеет **поток доставки** (не `Running`), стоп — через
  stopping-флаг + wake-батч в канал; watch() возвращает `Box<dyn Watcher>`, fallback на
  `PollWatcher` (2 с) при отказе recommended_watcher.
- Классификация: `Create(Folder)` → Rescan по `CreateKind`, не по `is_dir()` (путь может
  ещё не существовать в момент события); rename-цель без расширения → тоже Rescan.
- `Modified` существующих файлов идёт в события сразу (pull-протокол решает), через debounce
  идут только реально отсутствующие пути.
- Debounce-карта принадлежит AppState; при возврате файла в окно debounce отмена происходит
  на каждом тике, не только по истечении.
- `FsChangeEvent::Rescan` добавлен в enum; на UI — `invalidate_markdown_cache_and_tree` +
  `recheck_open_paths_after_rescan` (открытые пути скармливаются debounce).
- Конфликтная копия: имя `<stem> (конфликт YYYY-MM-DD HH-MM)[ N].<ext>` (UTC, без новых
  зависимостей), до 1000 попыток; буфер принимает дисковую версию, `reload` сбрасывает undo.
- Push-проверка: при неизвестном expected_hash (in-memory заметка) — прямая запись как раньше;
  при внешне удалённом файле — запись воссоздаёт файл (вкладку уже закрыл удалённый путь).

Постановка. Заменить опрос ФС (150 мс, `path.exists()` на UI-потоке) на событийный вотчер
по образцу `Aquilum/aquilum-app` (AGPL — переносим **приёмы и семантику**, не код).
Попутно оживляются мёртвые ветки `Modified`/`Renamed` и закрывается дыра потери данных:
сейчас автосейв молча затирает внешние правки файла.

Связанные планы: `perf-microfreezes-plan.md` §3 (здесь развёрнут), `perf-microfreezes-plan.md` §5
(reload_file_tree в фон — структурные события сюда же), `multi-document-workspace-plan.md`
(мультипанель), будущее многооконие.

## 1. Архитектура

### 1.1 Слои (переносим схему оригинала на наши сущности)

```
notify::recommended_watcher (root, Recursive)
        │  колбэк (поток notify)
        ▼
   classify(event, root) -> Option<RawEvent>          // fs_watcher/classify.rs
        │  mpsc
        ▼
   поток-доставщик: coalesce(80 мс) -> FsBatch        // fs_watcher/batch.rs
        │  mpsc
        ▼
   AppState.fs_events (Receiver)                      // владелец состояния
        │  drain (неблокирующий, тик 150 мс — существующий таймер main.rs)
        ▼
   AppState::handle_fs_batch(batch)                   // маршрутизация
        ├── Deleted  -> pending_deletions debounce -> handle_file_deleted
        ├── Renamed  -> handle_file_renamed
        ├── Modified -> pull-протокол (§3): dirty? stamp -> hash -> doc.reload
        └── Rescan   -> reload_file_tree (фон) + invalidate_markdown_cache
```

- **`fs_watcher`** — новый модуль без GPUI-типов (прецедент: `session_core/`), только
  `std`: `PathBuf`, `mpsc`, потоки. Три единицы: `Watcher` (start/stop/retarget),
  `classify`, `coalesce`.
- **`AppState`** — владелец вотчера, канала событий, `pending_file_deletions` и хешей диска.
  Не AppView: см. §4 (мультипанель/мультиокно).
- **UI-тик** — существующий таймер 150 мс из `main.rs` остаётся, но `poll_fs_changes`
  превращается в неблокирующий drain канала: ноль системных вызовов ФС, когда событий нет.
  Латентность реакции — до 150 мс + окно coalesce, как у оригинала (кадр), на практике
  неразличимо.

### 1.2 События (наша упрощённая классификация)

| Событие | Источник в classify | Действие |
| :--- | :--- | :--- |
| `Deleted(path)` | `Remove(File)` для md/текста | debounce 350 мс (существующий) → `handle_file_deleted` |
| `Renamed { from, to }` | `Modify(Name(Both))` с двумя путями | `handle_file_renamed`; пара tmp→md от атомарного сейва = `Modified(to)`, не удаление |
| `Modified(path)` | `Modify(Data(_))`, `Create(File)` (появился файл, который у нас открыт как отсутствующий) | pull-протокол §3 для открытых; для закрытых — ничего (индекс не держим) |
| `Rescan` | ошибка вотчера, `Remove(Folder)`, переполнение очереди | фон: `reload_file_tree` + `invalidate_markdown_cache` + сверка открытых путей |
| — | `Access(_)`, не-md/не-текст, скрытые пути | отсекается в classify |

## 2. Push-протокол: свои записи не видны и не затирают чужое

1. **Память хеша.** `DocumentBuffer` получает поле `disk_hash: Option<String>`:
   заполняется при `new`/`from_file` (SHA-256 содержимого; `sha2` уже в зависимостях),
   обновляется после каждой собственной записи.
2. **Свой writes не порождают действий.** Все пути записи (`save_document`,
   `flush_document_now`) после успешной записи обновляют `disk_hash`. Пришедший затем
   `Modified` от вотчера сравнит хеш диска с `disk_hash` — совпадение ⇒ no-op без чтения.
   Прямой write (<2 МБ) даст `Modify(Data)`, tmp+rename — `Rename(Both)`: оба покрыты.
3. **Конфликт вместо затирания.** Перед записью `safe_write_rope` вычисляет хеш текущего
   диска (фон, у `flush_document_now` уже есть фоновый поток; у синхронного `save_document`
   — там же, это редкий ручной путь). Хеш ≠ `disk_hash` ⇒ файл меняли извне:
   - записываем **конфликтную копию** рядом: `<Имя> (конфликт ГГГГ-ММ-ДД ЧЧ-ММ).md`
     (нумерация при занятости — по образцу `copy_path`+`first_free` оригинала);
   - буфер принимает дисковую версию? Нет — для активной заметки оригинал принимает
     дисковую версию и показывает статус. Повторяем: `doc.reload(диск)`, views dirty,
     `status_text = "Файл изменён извне; ваша версия сохранена в <копия>"`.
   - Undo-история буфера сбрасывается reload'ом (как сейчас `doc.reload`).
4. **Гонка двух наших записей** закрывается существующим `doc.version == version` в
   `flush_document_now` (аналог seq/after оригинала) — не трогаем.

Трёхстороннее слияние (`documents/session.rs:220-232`) — **фаза 2, вне скоупа**: требует
хранения base-текста на документ и merge-алгоритма. Фиксируется как будущий апгрейд;
конфликтная копия — корректный и безопасный первый уровень.

## 3. Pull-протокол: внешняя правка открытого файла

По `Modified(path)` для открытого документа (`handle_file_modified`, оживляется):

1. `doc.is_dirty` ⇒ только статус «файл изменён внешним приложением…» — **свои правки не
   затираем** (семантика уже написана, `state.rs:1565-1571`).
2. Иначе — двухступенчатая дешёвая проверка до чтения:
   - stamp `(len, mtime)` == запомненный ⇒ выход (метаданные совпали);
   - SHA-256 файла == `doc.disk_hash` ⇒ обновить stamp, выход (перезаписали тем же).
3. Только после промахов: `doc.reload(с диска)`, `disk_hash`/stamp обновить, views этого
   `doc_id` — `visual_cache_dirty = true` (уже так), статус «Файл обновлён».
4. Stamp хранится рядом с `disk_hash` (пара полей; при evict документа память уходит вместе
   с буфером и пересчитывается при следующей загрузке — приемлемо).

## 4. Мультипанель и будущее многооконие — инвариант размещения

- **Вотчер, канал событий, `pending_file_deletions`, `disk_hash`/stamp — только на уровне
  `AppState`.** `AppState` один и общий для всех листьев/сплитов — значит, вотчер один на
  приложение, все панели видят одни события. Запрещается держать что-либо из этого в
  `AppView` (по окну) — иначе два окна получат два вотчера на один корень и двойные события.
- **Маршрутизация по `doc_id`**, как `dispatch_edit_event`: `Modified` помечает dirty/перечитывает
  все view этого документа во всех листьях (не только активную панель). Сплиты с той же
  заметкой корректно обновятся; с другими заметками — не затронуты.
- **Перенацеливание** при `open_workspace_internal`: `watcher.watch(новый корень)` — старый
  останавливается (семантика `retarget` оригинала, `watcher/mod.rs:47-56`). Нет хранилища ⇒
  вотчер остановлен (сейчас опрос крутится всегда — это тоже уйдёт).
- **Настоящее второе окно.** Два сценария из анализа перф-плана:
  - окна делят `AppState` (ожидаемый путь) — получают вотчер и все протоколы бесплатно;
    ничего доделывать не нужно;
  - окно получит свой `AppState` — тогда **второй экземпляр вотчера на тот же корень**.
    Windows `ReadDirectoryChangesW` это выдерживает (несколько хендлов на каталог), события
    продублируются в оба состояния. Правило на будущее: один вотчер на корень на состояние;
    дедупликация между состояниями не нужна, конфликтная копия защищает от гонок записи.
  Это осознанное ограничение, фиксируем здесь, чтобы будущий window-manager не натыкался.
- «Move to new window» при появлении реального окна: заметка просто переезжает в окно с тем же
  `AppState` — протоколы не меняются.

## 5. Шаги

1. **Зависимости и скелет модуля.** `notify = "8"` в `Cargo.toml`; `src/fs_watcher/`:
   `mod.rs` (Watcher: start/stop/retarget, поток-доставщик), `batch.rs` (coalesce 80 мс),
   `classify.rs`. Типы: `FsBatch { paths, kind }`, `FsEventKind { Deleted, Renamed, Modified, Rescan }`.
   Юнит-тесты без ФС-событий (classify по синтетическим `notify::Event`, coalesce по каналу)
   + интеграционные на tempdir по образцу оригинальных: доставка события, retarget, тишина
   после stop, `RenameMode::Both` не создаёт Deleted.
2. **Владелец в AppState.** Поля `fs_watcher: Option<Watcher>`, `fs_rx: Option<Receiver<FsBatch>>`,
   перенос `pending_file_deletions` из AppView в AppState (AppView только передаёт свои
   остатки при вызове). `open_workspace_internal`: retarget/stop. Точка монтирования
   колбэка — `Arc<Mutex<Sender>>` из `Watcher`.
3. **Drain вместо опроса.** `check_fs_changes` переписывается: неблокирующий
   `try_recv`-цикл по каналу → `Vec<FsEvent>`; `pending_deletions` debounce сохраняется как
   есть (feeding из Deleted-событий); `path.exists()` и клонирование путей удаляются.
   Таймер 150 мс в `main.rs` остаётся как тик дренирования.
4. **Оживление Renamed.** `handle_file_renamed` уже есть; из classify пара
   `tmp → целевой.md` для файла, открытого у нас, трактуется как Modified целевого
   (собственный атомарный сейв) либо как Renamed (чужой) — по совпадению имени tmp
   (`.имя.pid.tmp` — наш собственный шаблон из `save_manager.rs:57`, узнаём свои).
5. **Pull-протокол (§3).** Поля `disk_hash`/`disk_stamp` в `DocumentBuffer`; заполнение при
   `new`/`from_file`; `handle_file_modified` добирает двухступенчатую проверку. SHA-256
   большого файла — потоково по чанкам rope при записи/по файлу при чтении (фоновый поток).
6. **Push-протокол (§2).** `safe_write_rope` → вариант с `expected_hash` и возвратом
   `Ok/Conflict`; конфликтная копия `preserve_copy`-образная функция в `save_manager.rs`;
   обновление `disk_hash` после записи во всех точках сейва.
7. **Rescan.** Ошибка вотчера/удаление папки → `reload_file_tree` в фоне (§5
   perf-microfreezes-plan), `invalidate_markdown_cache`, сверка открытых путей с диском
   (существующая `pending_deletions`-логика по каждому пути, одна волна).
8. **Снятие опроса.** Из `check_fs_changes` удалён цикл по документам с `exists()`;
   таймер теперь только drain. Ноль обращений к ФС в простое.
9. **Проверка.** `cargo check`/`cargo test` зелёные; новые тесты:
   - classify: Access отсечён, tmp→md = Modified, Rename(Both) = Renamed/Modified, папка = Rescan, ошибка = Rescan;
   - coalesce: 80 мс окно, дедуп, глубокий вид побеждает;
   - интеграция tempdir: удаление → вкладка закрыта (dirty-защита сохраняет), переименование → вкладка следует, внешняя правка чистой заметки → перечитка, правка dirty-заметки → только статус;
   - конфликт: внешняя правка + наш сейв → конфликтная копия создана, дисковая версия в буфере, ничего не потеряно;
   - мультипанель: два view одного doc, Modified → оба dirty;
   - собственный сейв не порождает перечитки/удаления (по hash-совпадению и Rename(Both)).

## 6. Риски и инварианты

- **Вотчер только в AppState** (§4) — нарушение правила ломает будущее многооконие.
- **Атомарный собственный сейв** не должен выглядеть удалением: `.имя.pid.tmp` → цель —
  Recognize our tmp-шаблон в classify до общей обработки Rename.
- **Debounce удалений сохраняем** (`pending_file_deletions`): некоторые ФС/сетевые диски
  шлют неполные события; возврат файла в окно debounce отменяет удаление — поведение уже
  протестировано, не выбрасывать.
- **Потокобезопасность**: колбэк notify не должен захватывать AppState — только Sender.
  AppState-сторона работает исключительно на UI-потоке (drain), мьютексов на состояние нет.
- **Компиляция notify 8 на Windows** — ReadDirectoryChangesW штатно; на сетевых путях
  `recommended_watcher` может отказать → PollWatcher-fallback c редким интервалом (шаг 1),
  иначе классификация всё равно та же.
- **Новые строки статуса** — русские, в существующем стиле `state.rs` (там уже хардкод
  «Файл изменён внешним приложением…»); i18n-перечень не расширяется, пока статус-тексты
  не переведены на `t()`.

## 7. Вне скоупа

- Трёхстороннее слияние при внешнем изменении (фаза 2; сейчас конфликтная копия).
- Локальный store/история версий документов (sqlite у оригинала) — отдельная постановка.
- Инкрементальный поисковый индекс — в плане `search-index-plan.md`, тут только
  инвалидация кеша списка файлов.
- MCP/плагинные события — наш `events.emit_vault` уже вызывается из точек сейва; его
  вызовы сохраняются при конфликте (событие по копии не эмитим).

## 8. Критерии готовности

1. В простое UI-поток не выполняет вызовов ФС (drain пустого канала — ноль syscall).
2. Удаление/переименование/внешняя правка файла сторонней программой отражаются во вкладках,
   проводнике и открытой заметке за ≤ ~250 мс.
3. Сценарий «оба редактировали» теряет ноль данных: наша версия — в конфликтной копии,
   дисковая — в буфере, статус показывает имя копии.
4. Собственные сейвы (прямой и атомарный) не порождают видимых событий пользователю.
5. Переключение хранилища перенацеливает вотчер; при отсутствии хранилища вотчер остановлен.
6. Все существующие тесты зелёные; новые из шага 9 — в репозитории.
