# План: перенос плавности из оригинального Aquilum (стенд, damage-регионы, glide)

**Статус: частично внедрено (2026-10-21).** Решение по объёму: damage-регионы (Фаза 2) и
Фенвик (1.2) отложены — выигрыш только в процентах GPU, цена высока (см. «Порядок и точка
решения» ниже). Внедрено: 0.1 (перцентили кадра в FPS-мониторе, debug-only) и 1.1
(glide-цепочка колеса, cargo test 437 зелёных). Остальное — разведка на полку: условия
возврата описаны в конце плана.

**Внедрённое (1.1):** `WheelEase` хранит bezier-кривую (P1 кодирует входную скорость,
P2 = (0.6, 1.0)), `velocity_at` численно, `wheel_glide_duration_secs` — длительность
2 × средний интервал трёх последних нотов (кламп 50–200 мс, сид после простоя). Ретаргет:
нота по ходу продлевает цель и наследует скорость; разворот — старт с живой позиции,
старое движение дотухает мягко. Под флагом `editor.wheelSmoothScroll`, вне флага поведение
не изменилось. Тесты: сохранение скорости между нотами, разворот без шага назад, посадка
точно в цель, длительность по каденсу.

**Внедрённое (0.1):** `log_fps_tick` печатает `frame_ms p50/p95/max` — интервалы между
рендер-вызовами (каденция, которую видит глаз); выброс 50 мс = видимый застой независимо
от среднего. Кольцо 4096 интервалов, очистка в тике.

**Найдено при проверке glide (2026-10-21): дрожание ползунка при драге/глайде.** Полная
высота документа = оценка + реальное окно + оценка; каждый прыжок окна (раз в ~1500 строк)
подмешивал в total разницу реальных и оценочных высот меняющегося диапазона (замер: до
2.8%). Ползунок рисуется из `scroll/max_scroll` — дрожал именно он, и стало заметно,
когда glide сделал скролл непрерывным. Фикс (семантика оригинала, align-on-jump):
`rebuild_visual_cache_with_headings` при **чистом** движении окна (правки/ревил/wrap
захватываются guard'ом) закрепляет высоту: `above_h` выводится из сохранённой Y-позиции
якорной строки (первая собственная строка, или содержащая — для тела схлопнутого фенса;
якорь обязан покрываться старым окном, иначе откат к оценке), `below_h` — из сохранённой
полной высоты. Отрицательный запас (реальные высоты переросли оценочный total первой
кори) — откат к оценке: одна коррекция, дальше якорь работает заново. `line_at_doc_y`
вне окна инвертирует теперь точную карту (`doc_y_of_line`), а не замороженную оценку —
иначе обратное отображение расходится с прямым и окно гонится за собственным якорем.
Тест `total_height_is_stable_while_the_window_travels` ужесточён: между коррекциями
total неподвижен бит-в-бит, коррекции ≤3 на весь обход, шаг ≤5%.

## Референс (что где в оригинале)

| Механизм | Файлы оригинала | Суть |
| :-- | :-- | :-- |
| Сдвиг пикселей при скролле | `render/scroll.rs` | Регион прокрутки публикует viewport+offset; трекер сдвигает нарисованные пиксели `copy_within`, растрируется только открывшаяся полоса |
| Damage-трекер | `render/damage/{mod,region,merge,sink,hash,stack,draws}.rs` (~800 строк) | Список отрисовок прошлого кадра с хешами; diff даёт Move-сдвиги и минимальные грязные прямоугольники; спрайты (thumb) штампуются отдельно |
| Частичный present | `output/dxgi.rs:91-117` | CPU-холст → `CopySubresourceRegion` только грязных областей в backbuffer → `Present1(DirtyRects)`; DWM перекомпозитует только испорченное |
| Glide колеса | `ui/scroll/glide.rs` | Каждая ступенька — bezier-твин к цели; `Wheel::retarget` продолжает **с цели и текущей скорости** глайда, длительность подстраивается под интервал нотов (2×, кламп 50–200 мс) |
| Ползунок | `ui/scroll/{bar,widget,input,area}.rs` | Драг = перевод координат + фаза compose Masonry двигает контент **без перерисовки**; перерисовывается только полоса/thumb |
| Оконный документ | `ui/editor/document/window.rs` | MARGIN=3000 строк, SPAN_BYTES=512КБ, догрузка на MARGIN/2, прыжок на y через оценку `byte_at` — у нас всё это уже есть (наша копия их дизайна) |
| Высоты | `ui/editor/document/heights.rs` | Дерево Фенвика: top/at/set за O(log n), splice+rebuild на правках |
| Кеш укладок | `ui/editor/document/layout/cache.rs` | per-line `laid: line → Layout+Decor`, `ensure(shown)`, `evict` непоказанных, правка инвалидирует ровно одну строку |
| Живой слой | `render/live.rs`, `host/frame.rs:76-93` | Мигание каретки — отдельный кадр поверх кешей, без пересборки сцены (наш дефернутый §1) |
| Стенд | `app/tests/perf/{big,cost,frames,timing,typing_memory}.rs`, `app/tests/damage/*` | Реальный event-loop с фиксированным кадром 8.33 мс: прыжки 0/50/95%, p50/p95/max флика, шаги ползунка по 1%, тачпад по 3 px, набор, простой; damage-сьют проверяет «прокрутка даёт Move и минимальные прямоугольники» |

Чего у нас **нет и не будет копией**: их CPU-холст (`copy_within` по пикселям) — у нас gpui
рисует GPU-квадраты. Damage у нас должен быть построен иначе (см. Фазу 2), но семантика
трекера (хеши отрисовок, Move, минимальные прямоугольники) переносится как идея.

## Фаза 0 — стенд и damage-инфраструктура (проверяемость, сначала)

Без этого любая работа по damage не проверяема. Три части:

### 0.1. Замер кадров в приложении (дёшево, сразу)

FPS-монитор уже считает render calls в секунду. Добавить **per-frame wall-time** в
`log_fps_tick` (app_view.rs) и печатать в тике p50/p95/max за секунду — как в их
`percentiles(&times, [0.5, 0.95, 1.0])`. Это главный индикатор для всей кампании: GPU-процент
в пиках нам уже знаком, а теперь будет и цена кадра по фазам (у оригинала в кадре меряют
scene/raster/present отдельно — у нас пока одним числом, расширение по желанию).
Файлы: `src/views/app_view.rs` (log_fps_tick), `src/perf.rs` (кольцо времён кадров).
Debug-only, в release по-прежнему ноль записей.

### 0.2. CPU-стенд сценариями (headless)

Бенчмарки в `src/perf.rs` уже меряют логику ввода (0.003–0.025 мс/символ). Добавить
**кадровые сценарии**: построение сцены видимого диапазона (те же шаги, что делает render:
slice строк, classify, shape через кеш, heights) на синтетических документах 50/5000/50 000
строк, p50/p95/max за цикл. Это ловит CPU-регрессии (микрофризы) до того, как они дойдут до
глаз. GPU-часть в headless не проверяется — её меряет 0.1.
Файл: `src/perf.rs` (новый тест-модуль), переиспользует `generate_test_doc`.

### 0.3. Damage-тесты (контракт до реализации)

Писать тесты **до** Фазы 2 — они и есть её спецификация. Модуль без GPU: на вход два кадра
(список отрисовок: хеш, rect, id региона прокрутки), на выходе — Move-сдвиги и минимальные
грязные прямоугольники. Сценарии (по образцу их damage-сьюта, формулировки свои):

- прокрутка на dy: ровно один Move + полоса открывшейся области, никаких полных кадров;
- прокрутка больше высоты вьюпорта: Move отменяется, грязный прямоугольник = весь вьюпорт;
- неизменный кадр: пустой diff;
- правка одной строки: грязный прямоугольник = строка ± паддинги, не весь вьюпорт;
- появление/исчезновение элемента: два минимальных прямоугольника (старое+новое место);
- thumb как «спрайт»: изменение цвета/позиции thumb'а даёт прямоугольник только thumb'а;
- свойство (property): сумма площадей грязных прямоугольников + площадь сдвига ≤ площадь
  изменившихся пикселей с запасом на наложение;
- глайд (перенос из 0.2 ниже, но поведенческий тест тут): серия нотов не даёт «присадку»
  между нотами; торможение монотонно; остановка точно в цели; пальцы без движения не флингуют.

Файл: `src/damage_tracker.rs` (+ тесты в нём) — сам трекер появится здесь же в Фазе 2,
тесты фиксируют API заранее. При Фазе 0 можно положить тесты `#[ignore]`-компилируемыми
или в отдельный `tests/damage_spec.rs` против фиктивной реализации — решается при старте
Фазы 0, лишь бы контракт был записан.

## Фаза 1 — дешёвые независимые переносы (можно параллельно с Фазой 0)

### 1.1. Glide-цепочка колеса

Наш `wheel_ease` (app_view.rs:1617-1658) уже копит цель от нота к ноту, но теряет скорость:
каждый нот — новая кривая с нулевой начальной скоростью → «присадка» между нотами. Порт
семантики их `Wheel::retarget`: `WheelEase` хранит текущую скорость; новый нот стартует с
живой позиции с этой скоростью, длительность = 2× среднего интервала нотов (кламп 50–200 мс),
кривая — наш `wheel_ease_factor` сохраняется (он проверен тестом). Работает под флагом
`editor.wheelSmoothScroll` — поведенческих рисков вне флага нет.
Файлы: `src/views/app_view.rs` (структура WheelEase, handle_editor_wheel, step_wheel_ease).
Тесты из 0.3 (глайд-сценарии).

### 1.2. Дерево Фенвика для VisualRowHeightIndex (опционально)

Наши базы по 256 блоков (markdown.rs:1117-1290) быстры, но `replace_rows` пересчитывает базы
впереди изменения O(n/256), а `top_of` — линейный проход внутри блока. Фенвик даёт строгие
O(log n) на всё и простой splice. Переносим семантику их `Heights` (values f32 + дерево f64,
`top/at/set/splice`). Ценность средняя: профилирование не показывало, что индекс высот —
узкое место. **Делать только если Фаза 2 покажет, что индекс греется.**

## Фаза 2 — damage-регионы в vendored gpui (большая, после Фазы 0)

Цель: убрать полнокадровую растеризацию и полный present — единственный оставшийся рычаг
GPU (записано в perf-input-latency-plan.md, «Итог кампании»).

Текущее состояние: `vendor/gpui/src/platform/windows/directx_renderer.rs:286-316` — `draw()`
рисует все пакеты сцены в backbuffer и зовёт полный `Present(0, 0)`. Наш локальный патч уже
пропускает present, когда кадр не грязный — это половина экономии в простое; damage съест
остальное (кадр набора/скролла).

Дизайн (наш, не их копия — у них CPU-холст, у нас GPU):

1. **Хеш-трекинг примитивов.** Сцена gpui — пакеты примитивов с уже готовыми rect'ами.
   Хешерируем каждый примитив (содержимое+геометрия) в стрим; храним прошлый кадр. База есть:
   сцена строится детерминированно, счётчики shape/inval уже分离ают «что изменилось».
2. **Move-сдвиг.** Для регионов прокрутки (наш слайс редактора — один большой регион) при
   смене offset: `CopyResource`/`CopySubresourceRegion` прошлого кадра со сдвигом dy в
   текущий backbuffer, растеризуются только открывшиеся полосы со scissor-ректом.
   Нюанс: backbuffer после Present не читается — нужен persistent offscreen-буфер кадра
   (texture), из которого и копируем, и который же служит источником для present.
3. **Scissor-рендер изменённых регионов.** Квадраты вне dirty-прямоугольников пропускаются
   (spatial-фильтр по rect'ам); paths/intermediate аналогично. Инкрементальность GPU-атласа
   уже есть.
4. **`Present1` с DirtyRects** вместо `Present` (dxgi.rs оригинала показывает API).
   Composition swapchain у нас в пути (`CreateSwapChainForComposition` на 1044) —
   проверить поддержку DirtyRects на этом пути; если нет, остаёмся на CopyResource-полосах,
   что уже снимает растеризацию (главную часть).
5. **Интеграция с нашей существующей правкой** (present-only-when-dirty) — damage-регионы её
   поглощают: пустой diff = нет present вовсе.

Оценка: самая крупная единица работы за всю кампанию (сотни строк в vendored gpui + трекер
из Фазы 0.3 + стенд как приёмка). Риски: сломать наш локальный патч vsync; сплиты и
панели в titlebar — регионы должны работать на каждый вьюпорт; DWM-окклюзия; device lost.
Инвариант не трогать: политика «мигание изолируется» из perf-plan-aquilum §1.5.

## Порядок и точка решения

1. Фаза 0 (стенд + контракт damage) — независимо и сразу.
2. Фаза 1.1 (glide) — независимо, малая; можно вместе с Фазой 0.
3. Замеры на Фазе 0: цена кадра при наборе/скролле/драге ползунка.
4. По замерам — решение о Фазе 2. Критерий запуска: цена кадра при скролле большого файла
   стабильно выше ~3 мс в release, и это чувствуется пользователем (рывки при драге ползунка).
5. Фенвик (1.2) — только по горячим профилям после Фазы 2.

## Риски / инварианты

- AGPL: никакой код из `Aquilum/aquilum-app` не копируется; пишем своё по семантике.
- Локальный патч vendored gpui (present-only-when-dirty) не сломать — Фаза 2 его поглощает.
- Новых UI-компонентов не заводим (AGENTS.md): трекер/стенд — не UI, glide — правка существующей логики.
- Debug-замеры шумят (сборка сама ест время): финальные цифры — только в release.
- Стенд не должен стать флейком: фиксированный кадр и синтетические документы, без реальных таймеров
  ФС/сети; wall-time в 0.1 — только как индикатор, пороги — в бенчмарках 0.2.
