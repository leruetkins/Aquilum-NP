# План: быстрый поиск — этап A (A1+A2+A5), затем этап B (свой индекс)

Источник идей: `../../Aquilum/aquilum-app/` (`core/src/search/*`, `core/src/text/matcher/*`,
`native/src/app/search/*`). Лицензия `aquilum-app` — **AGPL-3.0**: переносим **приёмы, не код**
(тот же вывод, что в `perf-plan-aquilum.md` §4.4).

Документ — рабочий план реализации. Номера строк — по состоянию на **2026-10-21**, ветка
`undo-redo` (d309306), проверены по коду. При правке кода привязки устаревают — искать по
именам символов, номера даны для ориентира.
Порядок: **сначала этап A** (A1 + A2 + A5), **затем этап B**.

```

src/search/fold.rs     // A1: матчер свёртки
src/search/worker.rs   // A5: воркер скана (+ кэш, см. A2/A5)
```

Кэш тел на этапе A остаётся в `goto_search.rs` (`SearchContentCache`); в `src/search/` он

### A1. Матчер свёртки вместо `to_lowercase()`

**Зачем.** Сейчас на каждый файл и на каждый символ строки создаётся строка в нижнем регистре —
и это повторяется на каждое нажатие даже при горячем кэше тел (свёртка не кэшируется,
`goto_search.rs:889,899`). Матчер сворачивает символ **на лету**, не аллоцируя, и сразу отдаёт
**байтовый диапазон в оригинале** — это чинит и производительность, и оговорку из комментария
`goto_search.rs:992` («экзотические регистры меняют длину») без хаков вроде `chars().count()`
для пересчёта индекса.

**API** (`src/search/fold.rs`):

```rust
#[derive(Clone, Copy, PartialEq, Eq)]
pub enum Fold { Exact, Lower }          // Exact — режим «Aa» (case_sensitive)

#[derive(Clone, Copy, PartialEq, Eq)]
pub enum Mode { Substring, WordPrefix, WholeWord }

/// Символы текста в свёрнутом виде вместе с диапазоном байт в ОРИГИНАЛЕ.
pub struct Folded<'a> { /* text, at, fold, expansion: [char; 8], len, pos */ }
impl Iterator for Folded<'_> { type Item = (char, std::ops::Range<usize>); }

pub fn contains(hay: &str, needle: &str, fold: Fold, mode: Mode) -> bool;
pub fn count(hay: &str, needle: &str, fold: Fold) -> usize;
pub fn find(hay: &str, needle: &str, fold: Fold, mode: Mode) -> Option<std::ops::Range<usize>>;
/// Непересекающиеся диапазоны по всем needle, длинные выигрывают (замена find_term_ranges_cased).
pub fn ranges(hay: &str, needles: &[&str], fold: Fold, limit: usize) -> Vec<std::ops::Range<usize>>;
```

**Приём (модель `Aquilum/aquilum-app/core/src/text/matcher/fold.rs`).** Таблица свёртки на
первые 0x800 кодов BMP, собранная один раз в `OnceLock`; для остального — `char::to_lowercase()`
посимвольно с раскрытием в стек-буфер на 8 `char` (для случаев вроде `İ` → `i` + точка).
Итератор отдаёт `(свёрнутый_char, диапазон_в_оригинале)`, поэтому подсветка и сниппет работают
с оригинальными байтами без обратного пересчёта. Референс строит таблицу прогоном
`tantivy::AsciiFoldingFilter` — у нас tantivy нет, поэтому таблица собирается стандартным
`char::to_lowercase()` (см. ниже про `Fold::Ascii`).

**Осознанно не берём** `Fold::Ascii` (диакритика): таблица диакритики — отдельная задача, на
этапе A достаточно `Lower` + корректных раскрытий.

**Что заменяем (без изменения поведения):**

| Сейчас | Станет |
| :--- | :--- |
| `fold()` `goto_search.rs:659` | удаляется |
| `name_folded.contains(&q)` `:741,763,884,885` | `fold::contains(.., Mode::Substring)` |
| свёртка тел в `match_any`/`Tag`/`Line`/`Section` `:779,799,824,889,899` | исчезает (свёртка на лету) |
| `count_occurrences` `:977` | `fold::count` |
| `first_line_matching` `:918` | `fold::contains` по строкам |
| `make_snippet` `:995` (пересчёт через `chars()`) | `fold::find` → байтовый диапазон в оригинале |
| `find_term_ranges_cased` `:1132` (посимвольный `to_lowercase` `:1165`) | `fold::ranges` |
| `highlight_query_terms_cased` `:1189` | без изменений (термы запроса короткие, сворачиваются один раз) |

**Ранжирование имён.** Заодно `Mode::WordPrefix` даёт тиры из `suggest/rank.rs` (начало имени →
начало слова → середина) — можно добавить как уточнение сортировки `goto_search.rs:868`, не ломая
текущий инвариант «имя раньше тела» (`:850-853`).

**Тесты** (модульные, в `fold.rs`; семантика — по референсу):
- регистр: кириллица, латиница, смешанный;
- раскрытие: `İ` → `i̇` — диапазон указывает на **один** исходный символ;
- `WordPrefix` не матчит середину слова; `Substring` матчит;
- `ranges` — непересекающиеся, длинный терм выигрывает, все границы на границах `char`;
- пустой needle → пусто; needle длиннее текста → пусто;
- многобайтовый запрос не паникует (`goto_search.rs:1937` уже есть такой тест — должен пройти).

### A2. Кэш тел уже есть — до-развить, не дублировать

**Факт.** `SearchContentCache` (`goto_search.rs:51-101`) уже решает задачу A2: штамп
`(len, mtime)`, бюджет 64 МБ, негативное кэширование файлов > `MAX_FILE_BYTES` и нечитаемых.
Заводить параллельный `src/search/cache.rs` — «вторая структура состояния для того же»
(запрещено §1 AGENTS.md). Плюс вариант «кэшируем только свёрнутое тело» из прежней редакции
плана **отклонён**: он ломает `Aa` (case-sensitive поиск по телу работает сегодня —
`GotoSearchParams.case_sensitive`, тест `case_sensitive_toggle` `:1956`) и заставляет
дочитывать сниппеты с диска, хотя сейчас они строятся из кэшированного оригинала бесплатно.

**Что делаем:**

1. **Диалог переходит на общий кэш.** `search_goto_files` (`:668-669`) сегодня создаёт новый
   `SearchContentCache` на каждый вызов — кэш для диалога мёртвый. Оба потребителя идут через
   единственный `AppView.search_content_cache` (`app_view.rs:241`); локальная обёртка
   `search_goto_files` удаляется (тесты вызывают `search_goto_files_opts` напрямую, `:1835`).
2. **Храним оригинал, как сейчас.** Свёртка — на лету A1-матчером (после A1 она бесплатна по
   памяти: ни аллокации). Кэшировать свёртку рядом с оригиналом — 2× памяти, не делаем.
3. **Вытеснение.** Существующий механизм «сброс целиком при 64 МБ» (`:87-90`) оставляем как есть;
   LRU-вытеснение — опциональная отдельная задача, в этап A не входит.
4. **Сброс при смене vault'а.** Сейчас его нет вовсе (`State` не достаёт до поля `AppView`;
   записи по путям чужого vault'а оседают мусором до переполнения бюджета). При переносе кэша
   в воркер (A5) `reset()` становится обязательным пунктом врезки в `open_workspace_internal`
   (`state.rs:1990`).
5. **Переезд в `src/search/` — один раз, вместе с воркером** (A5), а не двумя шагами.

**Точка врезки.** Сигнатура `search_goto_files_opts` (`:686`) уже принимает
`&mut SearchContentCache` — на этапе A её менять не нужно. Владелец кэша — **воркер** (см. A5):
UI-поток ФС не трогает вообще.

**Тесты:** попадание в кэш даёт тот же результат, что свежий скан; смена `mtime`/`size` —
инвалидация; файл > лимита не читается и не перечитывается на следующих нажатиях (негативное
кэширование уже есть — закрыть тестом); бюджет: переполнение сбрасывает кэш целиком;
case-sensitive и case-insensitive запросы по одному кэшу дают разные результаты (`Aa`).

### A5. Ввод не блокируется: дебаунс + вынос скана в фон + отмена

**Требование (господин).** Пока поиск уже начат, набор новых символов и стирание старых должны
обрабатываться немедленно — ввод не блокируется.

**Почему одного дебаунса мало.** Дебаунс лишь откладывает старт скана. Когда таймер сработает,
`run_goto_search()` (`goto_search.rs:257`) выполнится **в том же потоке UI** и на время
чтения/свёртки всех тел окно перестанет принимать клавиши. Дебаунс уменьшает число сканов, но
не убирает блокировку — наоборот, отложенный скан «съест» клавишу, набранную в этот момент.
Значит, скан обязан уехать из потока UI. Это и есть A5 в полном виде.

**Схема (три ступени, каждая снимает свою проблему):**

```
клавиша ──► 1. обновить query + cursor_pos, cx.notify()   ← всегда, немедленно, без поиска
         └─► 2. generation += 1; epoch += 1; таймер 70 мс  ← отмена старого + дебаунс
                 │  (по истечении, если epoch актуален)
                 └─► 3. скан в фоновом потоке (snapshot: query, op, cs, generation)
                          └─► mpsc ──► UI: применить, если generation актуален
```

1. **Обновление ввода — всегда первым и безусловно.** `query`, `cursor_pos`, `selection_anchor`
   меняются и `cx.notify()` вызывается до любой работы поиска. Каретка и текст перерисовываются
   сразу. Это и есть ответ на требование: поиск физически не может задержать ввод.
2. **Отмена старого запроса.** На каждое нажатие `generation += 1`. Фоновый скан периодически
   проверяет `generation.is_cancelled()` (идея `Aquilum/aquilum-app/core/src/text/cancel.rs` —
   `Generation`/`Cancel` на `AtomicU64`) и выходит досрочно, не дочитывая остаток файлов.
   Отмена обязательна уже на этапе A.
3. **Дебаунс** — тем же `epoch`-приёмом, что `BlinkManager::pause_and_show`
   (`src/blink_manager.rs:123`): `foreground_executor().spawn` + `timer_executor.timer(70 мс)` +
   проверка `epoch` внутри `update`. Дебаунс только снижает число запусков фонового скана.
4. **Скан — в фоне.** Движок `search_goto_files_opts` (`goto_search.rs:686`) остаётся **чистой
   функцией** (пути, запрос, параметры, кэш) → тестируется как сейчас. Асинхронная обёртка живёт
   отдельно: воркер владеет `SearchContentCache` и списком путей, UI шлёт запросы и читает ответы.

**API обёртки** (`src/search/worker.rs`):

```rust
pub struct SearchRequest { pub generation: u64, pub query: String, pub op: SearchOp,
                           pub case_sensitive: bool, pub limit: usize }
pub struct SearchReply  { pub generation: u64, pub results: Vec<GotoResult> }

pub struct SearchWorker {
    requests: mpsc::Sender<SearchRequest>,
    replies:  mpsc::Receiver<SearchReply>,
    cancel:   Cancel,             // Generation на AtomicU64
}
impl SearchWorker {
    pub fn spawn(workspace: Option<PathBuf>) -> Self;
    pub fn set_files(&self, files: Vec<PathBuf>);   // дерево перезагрузилось
    pub fn reset(&self, workspace: Option<PathBuf>); // смена vault'а: файлы + кэш
    pub fn ask(&self, req: SearchRequest);          // ставит Cancel и шлёт запрос
    pub fn try_recv(&self) -> Option<SearchReply>;
}
```

- **`SearchContentCache` переезжает в воркер целиком**, а `AppView.search_content_cache`
  (`app_view.rs:241`) **удаляется** — иначе останутся две копии кэша (дублирующее состояние,
  §1 AGENTS.md). После переезда UI-поток вообще не трогает ни ФС, ни мьютексы; `AppView` держит
  только `SearchWorker` и последний список результатов.
- **Список путей — в воркере.** UI присылает его при перезагрузке дерева, а не клонирует 2000
  `PathBuf` на каждый запрос. Точка обновления — там, где новое дерево попадает в `State`:
  `apply_file_tree` (`state.rs:2056`, асинхронный путь — основной) и конец `reload_file_tree`
  (`state.rs:2168`, синхронный путь). Фильтры обхода сохраняются — список берётся из
  `collect_goto_files` (`goto_search.rs:571`), правила `build_tree` (`state.rs:2111`: скрытые,
  `node_modules`, `target`, `.git`) не меняются.
- **`reset`** вызывается из `open_workspace_internal` (`state.rs:1990`) вместе с существующим
  `attach_fs_watcher` (`:1998`): без него кэш переживёт смену vault'а (мусор по чужим путям до
  переполнения бюджета).
- **Приём ответов** — существующим шаблоном: `cx.spawn` + опрос `try_recv()` по таймеру +
  `cx.notify()` (`src/main.rs:59,94`, `src/ipc.rs:125`). Применяем ответ, только если
  `generation` актуален.

**Поведение UI при активном поиске:**

- **Старые результаты не очищаются**, пока идёт новый запрос — список заменяется ответом с
  текущей `generation`. Так нет мигания и нет «пустого» кадра между нажатиями.
- **`selected_ix` клампится** при применении новых результатов: сейчас `results.get(selected_ix)`
  (`goto_search.rs:354`) при укорочении списка вернёт `None`, и Enter молча ничего не сделает.
- **Enter** по-прежнему обязан опираться на актуальные результаты: если запрос в полёте, Enter
  применяет последний **завершённый** ответ (он соответствует уже введённому тексту, т.к. ввод
  обрабатывается синхронно), а если ответа ещё не было ни одного — ничего не открывает.
- Занятость можно показать ненавязчиво (точка/подпись «поиск…»), но **не** блокирующим оверлеем;
  если делаем подпись — новая строка UI, значит через `locales/*.json` (`src/i18n.rs`), не
  литералом.

**Точки врезки.** Вызовы `run_goto_search()`/`run_sidebar_search()` **из ввода** заменяются на
`request_search(cx)`:

### Критерии приёмки этапа A

- **Ввод не блокируется:** при активном поиске набор символов и Backspace обрабатываются сразу
  (каретка и текст обновляются в том же кадре); UI не замирает ни на одном запросе.
- **Отмена работает:** набранная поверх идущего поиска буква досрочно завершает предыдущий скан
  (счётчик отмен растёт), а не ждёт его конца.
- Все существующие тесты `goto_search.rs:1750-1955` проходят без правок ожиданий.
- В пути поиска не осталось `to_lowercase()` по телам (grep по `src/search/` + `goto_search.rs`).
- Второе и последующие нажатия по неизменённому vault'у **не читают** тела из ФС (только
  `metadata()`) — у **обоих** потребителей.
- `Aa` работает по телу (case-sensitive) — тест `case_sensitive_toggle` (`:1956`) зелёный.
- Кэш один: `AppView.search_content_cache` удалён, кэш живёт в воркере; смена vault'а его сбрасывает.
- Результаты не мигают: список не очищается между нажатиями; `selected_ix` клампится.
- Поведение (ранги, сниппеты, операторы, `Aa`) визуально не меняется.

### Риски этапа A

- **Память кэша** — бюджет есть (64 МБ со сбросом целиком); следить, чтобы перенос в воркер его
  не потерял. LRU — опционально.
- **Совместимость поведения** — свёртка A1 не делает ASCII-фолдинга, поэтому «е» и «ё» остаются
  разными (как и сейчас: `to_lowercase()` их не смешивает). Регрессии нет, но и улучшения нет.
- **Перенос кэша в воркер** — обновить обоих потребителей и тесты в одном коммите; оставить
  вторую копию кэша в `AppView` нельзя.
- **Гонка «устаревший ответ»** — ответ фонового скана применяется **только** при совпадении
  `generation`; иначе на медленном диске старый скан перезапишет свежие результаты.
- **Enter и «ответ в полёте»** — Enter работает по последнему завершённому ответу; если ни одного
  ещё не было, Enter ничего не открывает (не должно открывать результат от предыдущего запроса).
- **Два потребителя, один воркер** — диалог «Перейти к файлу» и панель сайдбара шлют запросы в
  один воркер; `generation` должен быть общим, иначе открытие панели отменит поиск в диалоге
  (или наоборот). Решение: отдельный `SearchWorker` на каждый потребитель либо общий воркер с
  раздельными `Generation`. Выбрать при реализации шага A5(a).
- **Асинхронное дерево** — если `set_files` привязать только к синхронному пути, список в воркере
  промахнётся после фонового обхода; привязывать к `apply_file_tree` (`state.rs:2056`).

## 2. Этап B — свой минимальный инвертированный индекс

Выбор господина: **`HashMap<term, Vec<(doc, count)>>` в памяти + ручной BM25**, без внешних
зависимостей. Референс — образец архитектуры (поля `id/path/title/body`, тело не хранится,
сниппет читается лениво), не обязательная реализация. Реализуется **после** этапа A.

```
src/search/mod.rs      // + pub mod index; pub mod tokenize; pub mod bm25; pub mod query;
src/search/tokenize.rs // разбор текста на термы
src/search/index.rs    // Index, Postings, build/update
src/search/bm25.rs     // ручной BM25F
src/search/query.rs    // разбор запроса → план, выдача
src/search/worker.rs   // воркер: скан (этап A) + построитель индекса (этап B)
```

### B0. Модель данных

```rust
pub struct Doc {
    pub id: u32,
    pub path: PathBuf,
    pub rel: String,        // относительный слэш-путь
    pub title: String,      // file_stem
    pub title_len: u32,     // для нормы BM25
    pub body_len: u32,      // для нормы BM25
}

/// Одна карта термов; поля внутри posting'а, чтобы применять бусты без трёх карт.
pub struct Posting { pub doc: u32, pub title: u16, pub path: u16, pub body: u16 }

pub struct Index {
    docs: Vec<Doc>,
    by_path: HashMap<PathBuf, u32>,
    terms: BTreeMap<String, Vec<Posting>>,   // BTreeMap — ради префиксного range-скана
    total_title_len: u64,
    total_body_len: u64,
    version: u32,                            // ANALYZER_VERSION
}
```

`BTreeMap` вместо `HashMap` — чтобы префиксный запрос был `range(prefix..)` + `take_while`, без
полного обхода термов. Для 10⁴–10⁵ уникальных термов это дёшево и без внешних зависимостей.

Тело в индексе **не хранится** — только термы и длины. Сниппет для победителей читается из
кэша воркера (или с диска — модель `Aquilum/aquilum-app/core/src/search/hits/file.rs`), позиция
находится A1-матчером (байтовый диапазон в оригинале).

### B1. Токенизация

Простейшая, без стемминга (Snowball не берём — это зависимость):
1. вырезать YAML-frontmatter и подписи/URL markdown-ссылок (идея
   `Aquilum/aquilum-app/core/src/search/analyzer/sanitize.rs`);
2. разбить по не-алфавитно-цифровым;
3. свернуть регистр A1-матчером (`Fold::Lower`);
4. посчитать частоты по полям (`title`, `path`, `body`);
5. токен, перед которым стоит `#`, дополнительно индексируется как отдельный терм `#<токен>` —
   иначе оператор `tag:` (сегодня требует литеральный `#терм`, `goto_search.rs:775-780`)
   станет неотличим от обычного слова.

**Правило референса «отбросить термы короче 2 символов» НЕ переносим:** однобуквенный запрос по
телу сегодня находит любую подстроку; с отсечкой он перестанет находить вовсе. Отсекаем только
пустые токены.

`ANALYZER_VERSION: u32` — константа в `src/search/mod.rs`; смена правил → полная переиндексация.
Версию хранить рядом с индексом (в памяти достаточно: индекс не переживает перезапуск — см. B4).

### B2. BM25 (ручной)

Параметры — из уже существующих настроек `Bm25fParams` (`src/settings.rs:13`):
`k1 = 1.2`, `b_title = 0.3`, `b_body = 0.75`, `title_weight = 2.5`.

```
idf(t)      = ln(1 + (N - df + 0.5) / (df + 0.5))
tf_part(f)  = (tf * (k1 + 1)) / (tf + k1 * (1 - b + b * len_f / avg_len_f))
score(d, q) = Σ_t idf(t) * ( title_weight * tf_part(title)
                           + 2.0           * tf_part(path)
                           + 1.0           * tf_part(body) )
```

- **Веса полей без двойного буста.** `title_weight` из настроек задаёт вес поля `title`
  **напрямую** (по умолчанию 2.5), path 2.0, body 1.0 — никаких «5.0 поверх 2.5».
- **`k3` не участвует**: частота терма в *запросе* у нас всегда 1 (мешок слов), насыщение по
  запросу нечему применять. Поле `k3` в `Bm25fParams` остаётся как есть (не ломаем сериализацию
  настроек); чистка настроек — отдельно, если захочется.
- Точные совпадения — множитель ×2 (идея `combined_query` в
  `Aquilum/aquilum-app/core/src/search/query.rs:100`).

### B3. Запрос

Два режима, потому что UX сейчас разный:
- **Имя и путь** (как `SearchOp::File`/`Path`) — подстрока. Имена/пути для всех файлов лежат в
  `docs` и коротки, поэтому матчим A1-матчером по списку `docs` (это дёшево) — так сохраняется
  текущее поведение «середина имени тоже матчится».
- **Тело** (как `SearchOp::Any`/`Tag`/`Line`/`Section`) — **индекс как генератор кандидатов**:
  1. для каждого терма запроса `terms.range(t..=t_max_префикс)` берём точные и префиксные термы,
     объединяем их postings;
  2. кандидаты — **пересечение** документов по всем термам (требование «все термы»,
     `goto_search.rs:900`, сохраняется), сортировка по BM25, отсечение до
     `candidate_pool_size` (`settings.rs:63`, по умолчанию 256);
  3. **верификация по телу** кандидатов A1-матчером: `Any` — подстрока; `Line` — все термы на
     одной строке; `Section` — все термы в одной секции (`split_sections`, `goto_search.rs:953`);
     `Tag` — литеральный `#терм` в теле. Затем сниппеты и подсветка как в этапе A, отсечение до
     `limit`.

**Осознанное отступление от этапа A (записано заранее).** Кандидат обязан содержать каждый терм
запроса **началом слова** (префиксный матч по индексу); подстрока **внутри слова** («ивет» в
«привет») на этапе кандидатов не находится — финальная проверка по телу подстрочная, но
документ-кандидат должен сначала пройти через postings. Полная подстрочная семантика на
инвертированном индексе без n-грамм недостижима; n-граммы не берём (дорого, §3). Если при
приёмке выяснится, что внутрисловный recall критичен — запасной режим: ноль кандидатов при
непустом запросе → фолбэк на скан этапа A для этого запроса (стоимость = сегодняшняя). По
умолчанию считаем отступление приемлемым (так ищут все поисковики по словам).

Опечатки (fuzzy) — не берём на этапе B: в референсе это `FuzzyTermQuery` из tantivy, руками это
отдельный автомат. Отметить как возможное продолжение.

### B4. Воркер и доставка в UI

- **Воркер уже есть** — заведён на этапе A5 (`src/search/worker.rs`), владеет `SearchContentCache`
  и списком путей. На этапе B он получает ещё и `Index`; UI-часть не меняется.
- Построение индекса — в том же фоновом потоке; шаблон доставки: `mpsc` + опрос в `cx.spawn`
  раз в 100 мс + `cx.notify()` (`src/main.rs:59,94`, `src/ipc.rs:125`).
- **Фолбэк живёт внутри воркера, а не в UI.** Пока индекс строится, воркер отвечает по пути
  этапа A (скан с кэшем) — тот же формат `SearchReply`, тот же `generation`. Как только индекс
  готов, воркер переключается на него. Ключевое: поиск никогда не «молчит» в первые секунды, и
  требование «ввод не блокируется» выполняется на обоих путях одинаково.
- Индекс в памяти, **не персистится** (нет `rusqlite`): на открытии воркспейса строится заново,
  при перезапуске — снова. Для 10⁴–10⁵ заметок это секунды (фолбэк это время терпит);
  персистентность — отдельная задача.
- Прогресс и статус — по образцу `IndexProgress`/`SearchIndexStatus` референса, чтобы UI мог
  показать «индексирую…» (строка — через `locales/*.json`); карточка пустого состояния в
  `render_search_dialog` уже есть.

### B5. Инкрементальное обновление

- Точки сохранения файла: `src/state.rs:2694` (`save_active_note`), `src/views/app_view.rs:1099`
  — после записи уведомлять индекс об одном пути (переиндексировать только его).
- Полный rescan — при открытии воркспейса (`state.rs:1990`) и при смене дерева
  (`apply_file_tree` `:2056` / `reload_file_tree` `:2168`).
- **Вотчер ФС уже есть** (`src/fs_watcher/`, батчи текут в `state.fs_events_rx`,
  `state.rs:444`) — этап C теперь это **интеграция**: события батчей → инкрементальная
  переиндексация изменённых путей. Новых зависимостей и потоков не требуется.

### Критерии приёмки этапа B

- Поиск по телу на vault'е 10⁴ заметок — заметно быстрее этапа A; `metadata()`-проход по всем
  файлам на нажатие исчезает (индекс в памяти).
- Тело нигде не хранится в индексе (grep: в `Index` нет `String` с телом).
- **Фолбэк-путь**: тест-набор этапа A (`goto_search.rs:1750-1955`) проходит без правок ожиданий.
- **Индексный путь**: проходят все тесты, кроме осознанно ослабленных — тесты на внутрисловную
  подстроку по телу получают новые ожидания (префикс-от-слова), и это отступление записано в B3;
  `line:`/`section:`/`tag:` ведут себя как в этапе A (верификация по телу).
- Пока индекс строится, поиск работает по фолбэку (этап A), без пустого списка.
