## 1. Этап A — снять основную стоимость (A1 + A2 + A5)

### A1. Матчер свёртки вместо `to_lowercase()`

**Зачем.** Сейчас на каждый файл и на каждый символ строки создаётся строка в нижнем регистре.
Матчер сворачивает символ **на лету**, не аллоцируя, и сразу отдаёт **байтовый диапазон в
оригинале** — это чинит и производительность, и оговорку из комментария `goto_search.rs:921-923`
(«экзотические регистры меняют длину») без хаков вроде `chars().count()` для пересчёта индекса.

**API** (`src/search/fold.rs`):

```rust
#[derive(Clone, Copy, PartialEq, Eq)]
pub enum Fold { Exact, Lower }          // Exact — режим «Aa» (case_sensitive)

#[derive(Clone, Copy, PartialEq, Eq)]
pub enum Mode { Substring, WordPrefix, WholeWord }

/// Символы текста в свёрнутом виде вместе с диапазоном байт в ОРИГИНАЛЕ.
pub struct Folded<'a> { /* text, at, fold, expansion: [char; 8], len, pos */ }
impl Iterator for Folded<'_> { type Item = (char, std::ops::Range<usize>); }

pub fn contains(hay: &str, needle: &str, fold: Fold, mode: Mode) -> bool;
pub fn count(hay: &str, needle: &str, fold: Fold) -> usize;
pub fn find(hay: &str, needle: &str, fold: Fold, mode: Mode) -> Option<std::ops::Range<usize>>;
/// Непересекающиеся диапазоны по всем needle, длинные выигрывают (замена find_term_ranges_cased).
pub fn ranges(hay: &str, needles: &[&str], fold: Fold, limit: usize) -> Vec<std::ops::Range<usize>>;
```

**Приём (модель `aquilum-app/core/src/text/matcher/fold.rs`).** Таблица свёртки на первые 0x800
кодов BMP, собранная один раз в `OnceLock`; для остального — `char::to_lowercase()` посимвольно с
раскрытием в стек-буфер на 8 `char` (для случаев вроде `İ` → `i` + точка). Итератор отдаёт
`(свёрнутый_char, диапазон_в_оригинале)`, поэтому подсветка и сниппет работают с оригинальными
байтами без обратного пересчёта.

**Осознанно не берём** `Fold::Ascii` (диакритика): в референсе таблица строится прогоном
`tantivy::AsciiFoldingFilter` по всем символам, у нас tantivy нет. Своя таблица диакритики — потом,
отдельной задачей; на этапе A достаточно `Lower` + корректных раскрытий.

**Что заменяем (без изменения поведения):**

| Сейчас | Станет |
| :--- | :--- |
| `fold()` `goto_search.rs:600` | удаляется |
| `name_folded.contains(&q)` `:671, 692, 813` | `fold::contains(.., Mode::Substring)` |
| `count_occurrences` `:906` | `fold::count` |
| `first_line_matching` `:847` | `fold::contains` по строкам |
| `make_snippet` `:924` (пересчёт через `chars()`) | `fold::find` → байтовый диапазон в оригинале |
| `find_term_ranges_cased` `:1061` | `fold::ranges` |
| `highlight_query_terms_cased` `:1118` | без изменений (термы запроса сворачиваются один раз) |

**Ранжирование имён.** Заодно `Mode::WordPrefix` даёт тиры из `suggest/rank.rs` (начало имени →
начало слова → середина) — можно добавить как уточнение сортировки `goto_search.rs:797`, не ломая
текущий инвариант «имя раньше тела» (`:779-782`).

**Тесты** (модульные, в `fold.rs`; семантика — по референсу):
- регистр: кириллица, латиница, смешанный;
- раскрытие: `İ` → `i̇` — диапазон указывает на **один** исходный символ;
- `WordPrefix` не матчит середину слова; `Substring` матчит;
- `ranges` — непересекающиеся, длинный терм выигрывает, все границы на границах `char`;
- пустой needle → пусто; needle длиннее текста → пусто;
- многобайтовый запрос не паникует (`goto_search.rs:1864` уже есть такой тест — должен пройти).

### A2. Кэш тел файлов по `(mtime, size)`

**Зачем.** На нажатие перечитывать только изменившиеся файлы. Один `metadata()` на файл вместо
`read_to_string`.

**API** (`src/search/cache.rs`):

```rust
pub struct FileCache {
    workspace: Option<PathBuf>,
    entries: HashMap<PathBuf, Entry>,     // path -> свёрнутое тело
    order: VecDeque<PathBuf>,             // LRU
    bytes: usize,
    budget: usize,                        // по умолчанию 32 МБ
}
struct Entry { fingerprint: (u64, u64), folded: String }

impl FileCache {
    pub fn reset(&mut self, workspace: Option<PathBuf>);
    /// Свёрнутое тело файла; None — файл отсутствует или больше MAX_FILE_BYTES.
    pub fn folded_body(&mut self, path: &Path, fold: Fold) -> Option<&str>;
}
```

**Решение по памяти (важно).** Кэшируем **только свёрнутое тело** — 1× размер тела, с бюджетом и
LRU-вытеснением. Оригинал не храним: сниппет для ≤`MAX_RESULTS` (50) победителей дочитывается с
диска и матчится A1-матчером (он отдаёт диапазон в оригинале) — ровно модель референса
(«тело не хранится, сниппет читается лениво», `aquilum-app/core/src/search/hits/file.rs`).
Хранить и оригинал, и свёртку — 2× размер тела; для vault’а на 100 МБ это 200 МБ, неприемлемо.

**Инвалидация:**
- `fingerprint` не совпал (`mtime_ns` или `size`) → перечитать;
- файл больше `MAX_FILE_BYTES` (`goto_search.rs:30`) → не кэшировать (сейчас такие матчатся только
  по имени, `:664-667`);
- смена воркспейса → `reset()` по сообщению воркеру из `src/state.rs:1404` (`open_workspace`).

**Имена и пути не кэшируем.** `fold(&file_name)` и `fold(&rel_string)` — короткие строки; 2000
маленьких аллокаций на нажатие это микросекунды. Кэшируем только тела — там вся стоимость.

**Точка врезки.** `search_goto_files_opts` (`goto_search.rs:620`) получает `&mut FileCache` вместо
`std::fs::metadata`/`read_to_string` (`:664-667`). Владелец кэша — **воркер** (см. A5): UI-поток
ФС не трогает вообще. Сигнатуры `search_goto_files_opts`/`collect_goto_files` меняются — обновить
оба вызова и тесты.

**Тесты:** попадание в кэш даёт тот же результат, что свежий скан; смена `mtime`/`size` —
инвалидация; вытеснение по бюджету; файл > лимита не кэшируется; `reset` очищает.

### A5. Ввод не блокируется: дебаунс + вынос скана в фон + отмена

**Требование (господин).** Пока поиск уже начат, набор новых символов и стирание старых должны
обрабатываться немедленно — ввод не блокируется.

**Почему одного дебаунса мало.** Дебаунс лишь откладывает старт скана. Когда таймер сработает,
`run_goto_search()` (`goto_search.rs:191`) выполнится **в том же потоке UI** и на время чтения всех
тел (`:664-667`) окно перестанет принимать клавиши. То есть дебаунс уменьшает число сканов, но не
убирает блокировку — наоборот, отложенный скан «съест» клавишу, набранную в этот момент.
Значит, скан обязан уехать из потока UI. Это и есть A5 в полном виде.

**Схема (три ступени, каждая снимает свою проблему):**

```
клавиша ──► 1. обновить query + cursor_pos, cx.notify()   ← всегда, немедленно, без поиска
         └─► 2. generation += 1; epoch += 1; таймер 70 мс  ← отмена старого + дебаунс
                 │  (по истечении, если epoch актуален)
                 └─► 3. скан в фоновом потоке (snapshot: query, op, cs, generation)
                          └─► mpsc ──► UI: применить, если generation актуален
```

1. **Обновление ввода — всегда первым и безусловно.** `query`, `cursor_pos`, `selection_anchor`
   меняются и `cx.notify()` вызывается до любой работы поиска. Каретка и текст перерисовываются
   сразу. Это и есть ответ на требование: поиск физически не может задержать ввод.
2. **Отмена старого запроса.** На каждое нажатие `generation += 1`. Фоновый скан периодически
   проверяет `generation.is_cancelled()` (идея `aquilum-app/core/src/text/cancel.rs` —
   `Generation`/`Cancel` на `AtomicU64`) и выходит досрочно, не дочитывая остаток файлов.
   Теперь отмена **обязательна уже на этапе A**, а не «потом на B», как предполагалось раньше.
3. **Дебаунс** — тем же `epoch`-приёмом, что `BlinkManager::pause_and_show`
   (`src/blink_manager.rs:123-148`): `foreground_executor().spawn` + `timer_executor.timer(70 мс)` +
   проверка `epoch` внутри `update`. Дебаунс теперь только снижает число запусков фонового скана.
4. **Скан — в фоне.** Движок `search_goto_files_opts` (`goto_search.rs:620`) остаётся **чистой
   функцией** (пути, запрос, параметры, кэш) → тестируется как сейчас. Асинхронная обёртка живёт
   отдельно: воркер владеет `FileCache` и списком путей, UI шлёт запросы и читает ответы.

**API обёртки** (`src/search/worker.rs`, рядом с этапом B):

```rust
pub struct SearchRequest { pub generation: u64, pub query: String, pub op: SearchOp,
                           pub case_sensitive: bool, pub limit: usize }
pub struct SearchReply  { pub generation: u64, pub results: Vec<GotoResult> }

pub struct SearchWorker {
    requests: mpsc::Sender<SearchRequest>,
    replies:  mpsc::Receiver<SearchReply>,
    cancel:   Cancel,             // Generation на AtomicU64
}
impl SearchWorker {
    pub fn spawn(workspace: Option<PathBuf>) -> Self;
    pub fn set_files(&self, files: Vec<PathBuf>);   // дерево перезагрузилось
    pub fn ask(&self, req: SearchRequest);          // ставит Cancel и шлёт запрос
    pub fn try_recv(&self) -> Option<SearchReply>;
}
```

- **`FileCache` принадлежит воркеру**, а не `AppView`: тогда UI-поток вообще не трогает ни ФС, ни
  мьютексы. `AppView` держит только `SearchWorker` и последний список результатов.
- **Список путей — в воркере.** UI присылает его при перезагрузке дерева
  (`src/state.rs:1519` `reload_file_tree`), а не клонирует 2000 `PathBuf` на каждый запрос.
  Фильтры обхода остаются теми же — список берётся из `collect_goto_files` (`goto_search.rs:512`),
  так что правила `build_tree` (`src/state.rs:1469`: скрытые, `node_modules`, `target`, `.git`)
  сохраняются.
- **Приём ответов** — существующим шаблоном: `cx.spawn` + опрос `try_recv()` по таймеру + `cx.notify()`
  (`src/main.rs:92-138`, `src/ipc.rs:125`). Применяем ответ, только если `generation` актуален.

**Поведение UI при активном поиске:**

- **Старые результаты не очищаются**, пока идёт новый запрос — список заменяется ответом с текущей
  `generation`. Так нет мигания и нет «пустого» кадра между нажатиями.
- **`selected_ix` клампится** при применении новых результатов: сейчас `results.get(selected_ix)`
  (`goto_search.rs:295`) при укорочении списка вернёт `None`, и Enter молча ничего не сделает.
- **Enter** по-прежнему обязан опираться на актуальные результаты: если запрос в полёте, Enter
  применяет последний **завершённый** ответ (он соответствует уже введённому тексту, т.к. ввод
  обрабатывается синхронно), а если ответа ещё не было ни одного — ничего не открывает.
- Занятость можно показать ненавязчиво (точка/подпись «поиск…»), но **не** блокирующим оверлеем.

**Точки врезки.** Вместо прямых вызовов `run_goto_search()` из обработчика клавиш
(`goto_search.rs:370, 386, 422, 444`) и `run_sidebar_search()` из панели
(`search_panel.rs:337, 445, 460, 495, 516`) — `request_search(cx)`. Открытие/закрытие диалога
(`goto_search.rs:119`) и клики по результатам (`search_panel.rs:773, 797, 856, 930`) остаются
немедленными.

**Тесты:** движок — как сейчас (чистая функция); отдельно — что повторный `ask` отменяет предыдущий
скан (`Cancel` видит новую генерацию) и что ответ с устаревшей `generation` не применяется.

### Порядок работ этапа A

1. A1 (`fold.rs`) + переключение движка на него; прогнать существующие тесты `goto_search.rs`.
2. A2 (`cache.rs`) + протащить `&mut FileCache` через `search_goto_files_opts`.
3. A5 в два шага: (а) `worker.rs` — вынести скан в фон с `Cancel`; (б) дебаунс-обёртка в обоих
   потребителях. Шаг (б) без (а) бессмысленен: он не разблокирует ввод.
4. Замер: счётчик «сколько тел реально прочитано за нажатие» + счётчик «сколько раз скан был
   отменён» + `src/perf.rs`; сравнить до/после.

### Критерии приёмки этапа A

- **Ввод не блокируется:** при активном поиске набор символов и Backspace обрабатываются сразу
  (каретка и текст обновляются в том же кадре); UI не замирает ни на одном запросе.
- **Отмена работает:** набранная поверх идущего поиска буква досрочно завершает предыдущий скан
  (счётчик отмен растёт), а не ждёт его конца.
- Все существующие тесты `goto_search.rs:1680-1893` проходят без правок ожиданий.
- В пути поиска не осталось `to_lowercase()` по телам (grep по `src/search/` + `goto_search.rs`).
- Второе и последующие нажатия по неизменённому vault’у **не читают** тела из ФС (только `metadata()`).
- Результаты не мигают: список не очищается между нажатиями; `selected_ix` клампится.
- Поведение (ранги, сниппеты, операторы, `Aa`) визуально не меняется.

### Риски этапа A

- **Память кэша** — бюджет + LRU обязателен; иначе vault на 100 МБ съест 100 МБ RAM.
- **Совместимость поведения** — свёртка A1 не делает ASCII-фолдинга, поэтому «е» и «ё» остаются
  разными (как и сейчас: `to_lowercase()` их не смешивает). Регрессии нет, но и улучшения нет.
- **Сигнатуры движка меняются** — обновить оба потребителя и тесты в одном коммите.
- **Гонка «устаревший ответ»** — ответ фонового скана применяется **только** при совпадении
  `generation`; иначе на медленном диске старый скан перезапишет свежие результаты.
- **Enter и «ответ в полёте»** — Enter работает по последнему завершённому ответу; если ни одного
  ещё не было, Enter ничего не открывает (не должно открывать результат от предыдущего запроса).
- **Два потребителя, один воркер** — диалог «Перейти к файлу» и панель сайдбара шлют запросы в один
  воркер; `generation` должен быть общим, иначе открытие панели отменит поиск в диалоге (или наоборот).
  Решение: отдельный `SearchWorker` на каждый потребитель либо общий воркер с раздельными
  `Generation`. Выбрать при реализации шага A5(a).

## 2. Этап B — свой минимальный инвертированный индекс

Выбор господина: **`HashMap<term, Vec<(doc, count)>>` в памяти + ручной BM25**, без внешних
зависимостей. Референс — образец архитектуры (поля `id/path/title/body`, тело не хранится, сниппет
читается лениво), не обязательная реализация. Реализуется **после** этапа A.

```
src/search/mod.rs      // + pub mod index; pub mod tokenize; pub mod bm25; pub mod query; pub mod worker;
src/search/tokenize.rs // разбор текста на термы
src/search/index.rs    // Index, Postings, build/update
src/search/bm25.rs     // ручной BM25F
src/search/query.rs    // разбор запроса → план, выдача
src/search/worker.rs   // (этап A) воркер скана; на этапе B принимает ещё и построитель индекса
```

### B0. Модель данных

```rust
pub struct Doc {
    pub id: u32,
    pub path: PathBuf,
    pub rel: String,        // относительный слэш-путь
    pub title: String,      // file_stem
    pub title_len: u32,     // для нормы BM25
    pub body_len: u32,      // для нормы BM25
}

/// Одна карта термов; поля внутри posting'а, чтобы применять бусты без трёх карт.
pub struct Posting { pub doc: u32, pub title: u16, pub path: u16, pub body: u16 }

pub struct Index {
    docs: Vec<Doc>,
    by_path: HashMap<PathBuf, u32>,
    terms: BTreeMap<String, Vec<Posting>>,   // BTreeMap — ради префиксного range-скана
    total_title_len: u64,
    total_body_len: u64,
    version: u32,                            // ANALYZER_VERSION
}
```

`BTreeMap` вместо `HashMap` — чтобы префиксный запрос был `range(prefix..)` + `take_while`, без
полного обхода термов. Для 10⁴–10⁵ уникальных термов это дешево и без внешних зависимостей.

Тело в индексе **не хранится** — только термы и длины. Сниппет для победителей читается с диска
(модель `aquilum-app/core/src/search/hits/file.rs`), offset ищется A1-матчером.

### B1. Токенизация

Простейшая, без стемминга (Snowball не берём — это зависимость):
1. вырезать YAML-frontmatter и подписи/URL markdown-ссылок (идея
   `aquilum-app/core/src/search/analyzer/sanitize.rs`);
2. разбить по не-алфавитно-цифровым;
3. свернуть регистр A1-матчером (`Fold::Lower`);
4. отбросить термы короче 2 символов;
5. посчитать частоты по полям (`title`, `path`, `body`).

`ANALYZER_VERSION: u32` — константа в `src/search/mod.rs`; смена правил → полная переиндексация.
Версию хранить рядом с индексом (в памяти достаточно: индекс не переживает перезапуск — см. B4).

### B2. BM25 (ручной)

Параметры — из уже существующих настроек `Bm25fParams` (`src/settings.rs:13`):
`k1 = 1.2`, `k3 = 8.0`, `b_title = 0.3`, `b_body = 0.75`, `title_weight = 2.5`.

```
idf(t)      = ln(1 + (N - df + 0.5) / (df + 0.5))
tf_part(f)  = (tf * (k1 + 1)) / (tf + k1 * (1 - b + b * len_f / avg_len_f))
score(d, q) = Σ_t idf(t) * ( title_weight * tf_part(title)
                           + path_weight  * tf_part(path)
                           + body_weight  * tf_part(body) )
```

Веса полей — как в референсе (`query.rs`): title 5.0 / path 2.0 / body 1.0; `title_weight` из
настроек применяется поверх. Точные совпадения — множитель ×2 (идея `combined_query` в
`aquilum-app/core/src/search/query.rs:90-119`).

### B3. Запрос

Два режима, потому что UX сейчас разный:
- **Имя и путь** (как `SearchOp::File`/`Path`) — подстрока. Имена/пути для всех файлов лежат в
  `docs` и коротки, поэтому матчим A1-матчером по списку `docs` (это дёшево) — так сохраняется
  текущее поведение «середина имени тоже матчится».
- **Тело** (как `SearchOp::Any` / `Tag` / `Line` / `Section`) — через индекс: для каждого терма
  запроса `terms.range(t..)` берём точные и префиксные термы, объединяем postings, считаем BM25.
  Требование «все термы» (`goto_search.rs:829`) сохраняем: кандидаты — пересечение по множеству
  документов, а не объединение.

Опечатки (fuzzy) — не берём на этапе B: в референсе это `FuzzyTermQuery` из tantivy, руками это
отдельный автомат. Отметить как возможное продолжение.

### B4. Воркер и доставка в UI

- **Воркер уже есть** — заведён на этапе A5 (`src/search/worker.rs`), владеет `FileCache` и списком
  путей. На этапе B он получает ещё и `Index`; UI-часть не меняется.
- Построение индекса — в том же фоновом потоке; шаблон доставки: `mpsc` + опрос в `cx.spawn`
  раз в 100 мс + `cx.notify()` (`src/main.rs:92-138`, `src/ipc.rs:125`).
- **Фолбэк живёт внутри воркера, а не в UI.** Пока индекс строится, воркер отвечает по пути этапа A
  (скан с кэшем) — тот же формат `SearchReply`, тот же `generation`. Как только индекс готов,
  воркер переключается на него. Ключевое: поиск никогда не «молчит» в первые секунды, и
  требование «ввод не блокируется» выполняется на обоих путях одинаково.
- Индекс в памяти, **не персистится** (нет `rusqlite`): на открытии воркспейса строится заново,
  при перезапуске — снова. Для 10⁴–10⁵ заметок это секунды; персистентность — отдельная задача.
- Прогресс и статус — по образцу `IndexProgress`/`SearchIndexStatus` референса, чтобы UI мог
  показать «индексирую…» (у нас уже есть карточка пустого состояния в
  `render_search_dialog`).

### B5. Инкрементальное обновление

- Точки сохранения файла: `src/state.rs:1975` (`save_active_note`), `src/views/app_view.rs:802` —
  после записи уведомлять индекс об одном пути (переиндексировать только его).
- Полный rescan — при открытии воркспейса (`src/state.rs:1404`) и при смене дерева.
- Живой вотчер ФС (`notify`) — **не этап B**, а отдельный этап C: новая зависимость и новый поток.

### Критерии приёмки этапа B

- Поиск по телу на vault’е 10⁴ заметок — заметно быстрее этапа A; `metadata()`-проход по всем
  файлам на нажатие исчезает (индекс в памяти).
- Тело нигде не хранится в индексе (grep: в `Index` нет `String` с телом).
- Поведение запросов (ранги, сниппеты, все операторы, `Aa`) совпадает с этапом A — тот же
  тест-набор `goto_search.rs:1680-1893` должен проходить и на индексном пути.
- Пока индекс строится, поиск работает по фолбэку (этап A), без пустого списка.

## 3. Что осознанно НЕ берём

| Не берём | Почему |
| :--- | :--- |
| `tantivy` | Тяжёлая зависимость; господин выбрал свой минимальный индекс |
| `rusqlite` / SQLite-метаданные | Индекс в памяти, персистентность не требуется на B |
| `walkdir`, `notify` | Обход уже есть (дерево сайдбара); вотчер — этап C |
| Snowball-стемминг | Зависимость; для префиксного поиска не обязателен |
| `Fold::Ascii` (диакритика) | Нужна таблица; отдельной задачей |
| Fuzzy-запросы | Требует автомата; возможное продолжение после B |
