## 2. Расширения Zed: что умеют и как устроены

**Что расширения дают (по документации):** языки, дебаггеры, темы, иконки, сниппеты, MCP-серверы. По вызовам в `wasm_host.rs` видно, что процедурная часть (WASM) используется для: команды и настроек языкового сервера, подписей для автодополнения и символов, слэш-команд, конфигурации контекстных серверов (MCP), индексации документации и отладочных адаптеров. **В прочитанных источниках расширения не создают панели и окна.** Поэтому декларативный UI, модальные окна и размещение видов в нашем проекте это собственная разработка (core §5, §12.6–12.8), а не заимствование.

**Формат:** репозиторий Git с `extension.toml`:

```toml
id = "my-extension"
name = "My extension"
version = "0.0.1"
schema_version = 1
authors = ["Your Name <you@example.com>"]
description = "Example extension"
repository = "https://github.com/your-name/my-zed-extension"
```

Рядом лежат необязательные части: `languages/`, `themes/`, `snippets/` и, если нужен код, `Cargo.toml` с `crate-type = ["cdylib"]`, зависимость `zed_extension_api`, структура с трейтом `Extension` и макрос `register_extension!`. Цель компиляции `wasm32-wasip2`.

**Разработка:** «Install Dev Extension» ставит расширение из папки без публикации и перекрывает опубликованную версию. Вывод в `stdout` и `stderr` пробрасывается в процесс Zed (виден при запуске с `--foreground`). Документация предупреждает, что в WASM не работают `cfg`-директивы и `std::env::var`, и предлагает `current_platform` и методы `Worktree`.

**Что берём:**
- идею «установить для разработки из папки»: наше «Установить плагин для разработки» (WASM §8, JS §8.4);
- идею макроса регистрации и крейта SDK: `aquilum_plugin` с `register_plugin!` (WASM §5);
- манифест как файл рядом с бинарником и `schema_version` (у нас `apiVersion`, core §3).

## 3. WASM-хост Zed (`wasm_host.rs`)

| Деталь | Что сделано в Zed | Что у нас |
|---|---|---|
| Engine | Один глобальный `wasmtime::Engine` (`OnceLock`): компонентная модель, async, инкрементальная компиляция с кэшем (`moka`, до 32 МБ, вес записи это размер ключа и значения), epoch interruption | То же, но тик 10 мс и отдельный поток тиков (WASM §4.1), кэш предкомпиляции с оговорками (WASM §4.6) |
| Эпохи | Тик каждые 100 мс из задачи на executor GPUI; `store.set_epoch_deadline(1)` и `epoch_deadline_async_yield_and_update(1)`: плагин уступает executor на каждом тике, но не прерывается | Прерываем по бюджету времени, а не уступаем (WASM §4.3). В комментарии Zed сам отмечает, что тики безопаснее делать на неасинхронном потоке |
| Расширение | `WasmExtension { tx, manifest, work_dir, zed_api_version, _task }`. `tx` это канал **замыканий** `ExtensionCall = Box<dyn FnOnce(&mut Extension, &mut Store<WasmState>) -> BoxFuture>`. Метод `call` кладёт замыкание в канал и ждёт результат через `oneshot`. `Drop` закрывает канал | Тот же приём, но канал несёт **данные** (`PluginCall`), а не замыкания (WASM §2, §4.5): запросы можно проверять и сериализовать |
| Обратные вызовы в главный поток | `WasmState::on_main_thread`: замыкание уходит в `main_thread_message_tx`, его принимает задача на executor GPUI и выполняет с `AsyncApp`, результат возвращается через `oneshot` | `HostApi::submit` и мост `start_bridge` (core §12.2), ответ событием `HostEvent::Response` |
| Загрузка | Компиляция компонента на фоновом executor GPUI, инстанцирование и цикл сообщений на tokio (`gpui_tokio::Tokio::spawn`), потому что `wasmtime_wasi` использует tokio | Своя задача на плагин с маленьким tokio-рантаймом (WASM §4.5) |
| Версия API | Хост разбирает **весь** wasm до использования `wasmtime` (`wasmparser`), ищет custom section `zed:api-version` (6 байт: major, minor, patch как `u16` big-endian). Комментарий: так невалидные байты дают ошибку, а не панику внутри `wasmtime`. Биндинги выбираются по версии (`Extension::instantiate_async(..., zed_api_version, ...)`) | Секция `aquilum:api-version`, та же схема, проверка совпадения с манифестом (WASM §5, §6) |
| WASI | Расширению даётся рабочая папка `work_dir/<id>` как `preopened_dir` (и как `.`, и по абсолютному пути) с полными правами, `inherit_stdio`, переменные `PWD` и `RUST_BACKTRACE=full` | Строже: **без папок, окружения и сокетов**, файлы только через `host.vault-*` (WASM §4.2) |
| Права | `granted_capabilities` читаются из настроек пользователя; в `WasmState` лежит `CapabilityGranter::new(granted_capabilities, manifest)`. Конкретные типы возможностей и сама проверка в прочитанных файлах не видны (насколько мне известно, это запуск процессов, скачивание файлов и установка npm-пакетов) | Права из манифеста плюс решение пользователя, проверка в каждом вызове (core §12.3) |
| Запись файлов | `writeable_path_from_extension` (подробно ниже) | Тот же алгоритм для всего vault (core §12.4) |

### 3.1 `writeable_path_from_extension`: алгоритм

1. Канонизировать рабочую папку хоста и взять `<work_dir>/<id>` как разрешённую область.
2. Если путь относительный, присоединить его к этой области, иначе взять как есть.
3. **Лексически нормализовать** (`normalize_lexically`): `..` разрешается без обращения к файловой системе, выход выше корня это ошибка.
4. Найти **ближайшего существующего предка** и вызвать для него `canonicalize` (так раскрываются симлинки на диске). Несуществующие компоненты запоминаются как «хвост».
5. Присоединить хвост к канонизированному предку.
6. Проверить, что результат начинается с разрешённой области, иначе ошибка.

Тесты Zed покрывают: симлинк, указывающий наружу; `..` наружу; легитимный путь внутри; относительный путь с несуществующими промежуточными папками (должен проходить); симлинк «глубже» первого несуществующего компонента (должен отклоняться). Мы повторяем этот набор и добавляем Windows-варианты (core §12.4).

**Чем наш вариант отличается:** область у нас это vault, а не рабочая папка плагина, и добавлена проверка служебной папки `.vault/`. Остаточный риск (подмена симлинка между проверкой и открытием, TOCTOU) описан в core §12.4.

### 3.2 Чего в прочитанных файлах нет

Я не видел в `wasm_host.rs` и в документации никакой **пробной проверки расширения перед запуском** (аналога нашего `plugin-verify`, core §6.1). Защита там держится на изоляции WASM, правах и процессе публикации в каталог. Страницы документации про публикацию (лицензии, требования, ревью) я не читал, поэтому не утверждаю, как именно устроено ревью.

## 4. Панели и раскладка (`dock.rs`)

### 4.1 Трейт `Panel` и стирание типа

`Panel` это трейт, который реализует каждая панель (`Focusable + EventEmitter<PanelEvent> + Render`). Основные методы: `persistent_name`, `panel_key`, `position`, `position_is_valid`, `set_position`, `default_size`, `min_size`, `initial_size_state`, `icon`, `icon_tooltip`, `toggle_action`, `activation_priority`, `set_active`, `is_zoomed`, `set_zoomed`, `starts_open`, `enabled`. События панели: `PanelEvent::{ZoomIn, ZoomOut, Activate, Close}`.

Для хранения разных панелей в одном списке есть объектно-безопасный трейт `PanelHandle`, реализованный для `Entity<T>` где `T: Panel`. Это тот же приём, что `ItemHandle` для `Entity<T: Item>` в `item.rs`. **Берём** для видов плагинов: встроенные и плагинные виды хранятся как `Arc<dyn ViewHandle>` (core §12.6).

### 4.2 `Dock`

`Dock` это контейнер у одного края окна с фиксированной позицией (`Left`, `Bottom`, `Right`). Поля: список `panel_entries`, индекс активной панели `active_panel_index`, `is_open`, сериализованное состояние `serialized_dock`, слой модальных окон `modal_layer`. Что важно:

- **Порядок кнопок.** При добавлении панель вставляется бинарным поиском по `activation_priority`. Совпадение приоритетов в debug-сборке вызывает `panic` («Each panel must have a unique priority»). **У нас иначе:** порядок задаёт пара `(priority, plugin_id)`, поэтому совпадение приоритетов у разных плагинов не может уронить приложение (core §12.6, п. 6).
- **Смена позиции.** При изменении настройки панель переносится в другой `Dock`. Размер сохраняется, если ось та же (лево и право), и сбрасывается при смене оси (с боковой на нижнюю). Видимость и активность сохраняются. **Берём** (core §12.6, п. 7).
- **Размеры.** `PanelSizeState { size: Option<Pixels>, flex: Option<f32> }`. Сохраняются в KV-хранилище в области `dock_panel_size` по ключу `"{workspace_id}:{panel_key}"`; запись выполняется через `cx.defer` после изменения. Двойной клик по ручке изменения размера (6 пикселей) сбрасывает размер к значению по умолчанию. `clamp_panel_size` не даёт панели стать больше окна. Изменение размера отключено, пока открыт модальный слой или зум.
- **Зум.** Одновременно увеличена может быть только одна панель (`set_panel_zoomed` сбрасывает остальные) и после изменения сериализуется рабочая область.
- **Восстановление.** `restore_state`: по сохранённому `persistent_name` находится активная панель, затем применяются `visible` и `zoom`. Вызывается при каждом добавлении панели, поэтому панель, которая появилась позже (например, после загрузки плагина), получает своё сохранённое состояние. **Берём** для случая «плагин загрузился позже» (core §12.6, п. 4).
- **Кнопки панелей** в строке состояния (`PanelButtons`): значок, подсказка, счётчик (`icon_label`). Контекстное меню: «Dock Left/Right/Bottom» (только допустимые позиции), «Flex Width/Fixed Width», скрыть кнопку. Метод `move_to_next_position` переключает позиции по кругу среди допустимых.

### 4.3 Что не берём

Привязку к настройкам `settings` и `SettingsStore`, action-систему (`toggle_action`) и фокус-логику (`FocusHandle`) переносить как есть не нужно: это инфраструктура Zed. Нам нужна **модель** (позиции, группы вкладок, состояния, сохранение), а реализация будет своя на GPUI.

## 5. Вкладки и сериализация (`item.rs`)

- `Item` это трейт содержимого вкладки: `tab_content_text`, `tab_icon`, `to_item_events`, `is_dirty`, `can_save`, `save`, `can_split`, `clone_on_split`, `deactivated`, `workspace_deactivated`, `navigate`, `breadcrumbs`, `handle_drop`, `tab_extra_context_menu_actions` и др. События элемента сводятся к четырём общим: `ItemEvent::{CloseItem, UpdateTab, UpdateBreadcrumbs, Edit}` через `to_item_events`. **Берём** идею: вид плагина сообщает хосту только небольшой набор общих событий (обновить заголовок, закрыть), остальное хост не интерпретирует.
- `SerializableItem`: `serialized_item_kind`, `serialize(..., closing, ...)`, `deserialize(...) -> Task<Result<Entity<Self>>>`, `cleanup(workspace_id, alive_items)`, `should_serialize(event)`. Реестр (`SerializableItemRegistry`) по виду находит обработчик. **Берём** как `getState`/`setState` и реестр видов по `view_type` (core §12.6).
- **Повреждённые элементы.** Для ошибок открытия есть `InvalidItemView` и `ProjectItem::for_broken_project_item`: вместо падения показывается элемент, который объясняет ошибку. **Берём** как заглушку для плагина, которого нет или который не загрузился (core §12.6, п. 3).
- **Автосохранение.** В `added_to_pane` на событие `Edit` запускается отложенное действие с debounce (`DelayedDebouncedEditAction`) при настройке `AfterDelay { milliseconds }`. При настройке `OnFocusChange` потерявший фокус элемент попадает в список отложенных сохранений, который сбрасывается позже, после обработки всех событий фокуса и только если нет активного модального окна. **Берём** для сохранения раскладки (debounce 500 мс, core §12.6, п. 2) и для автосохранения заметок.
- **Подключение к рабочей области.** В `added_to_pane` элемент подписывается на свои события, получает историю навигации, ставится в очередь сериализации, а при освобождении (`observe_release_in`) подписки и записи снимаются. **Берём** как правило: всё, что регистрирует вид или плагин, снимается автоматически при его удалении (core §12.10).
- `FollowableItem` (режим «следовать за коллегой») для нас не нужен.

## 6. Сводная таблица: берём или делаем иначе

| Область | Что сделано в Zed | Что берём |
|---|---|---|
| Расширения | Rust компилируется в WASM (`wasm32-wasip2`), крейт `zed_extension_api`, манифест `extension.toml`. Расширения дают языки, темы, иконки, сниппеты, дебаггеры, MCP-серверы. **В прочитанных источниках панели и окна расширения не создают.** | Модель изоляции, права, версионирование. Декларативный UI плагинов (core §5, §12.7) придётся проектировать самим, готового аналога в Zed нет |
| Хост | `wasmtime`, один общий `Engine`, **epoch interruption** (тик раз в 100 мс), у каждого расширения свой `Store` и своя задача, которая принимает вызовы из канала. Результат возвращается через `oneshot`. Обратные вызовы в главный поток идут тоже через канал | Тот же паттерн для JS (поток на плагин, JS §4) и для WASM (WASM §2, §4), с каналом данных вместо замыканий |
| Права | `granted_capabilities` из настроек пользователя (конкретный перечень и проверка в прочитанных файлах не видны; насколько мне известно, это запуск процессов, скачивание файлов, установка npm), проверка в `CapabilityGranter` | Права из манифеста плюс решение пользователя (core §12.3) |
| Файлы | Расширение видит только свою рабочую папку. Для записи путь проходит `writeable_path_from_extension`: лексическая нормализация, `canonicalize` ближайшего существующего предка, проверка префикса. В тестах: симлинк наружу, `..`, вложенные несуществующие каталоги | Алгоритм из core §12.4 |
| Версия API | В wasm-файле лежит custom section `zed:api-version` | `apiVersion` в манифесте и проверка при загрузке (core §3, WASM §6) |
| Панели | Трейт `Panel` (`persistent_name`, `panel_key`, `position`, `default_size`, `min_size`, `icon`, `toggle_action`, `activation_priority`, `set_active`, зум). `Dock` хранит список панелей, индекс активной и `is_open`. События панели: `ZoomIn`, `ZoomOut`, `Activate`, `Close`. Размеры сохраняются в KV-хранилище по ключу «workspace:panel_key» | Модель раскладки (core §12.6) |
| Вкладки | Трейт `Item` (`tab_content_text`, `tab_icon`, `to_item_events`, `is_dirty`, `can_split` и т.д.) и `SerializableItem` (`serialized_item_kind`, `serialize`, `deserialize`). Стирание типа через `ItemHandle`, реализованный для `Entity<T>` | Тот же приём для видов плагинов (core §12.6) |
| Восстановление | При добавлении панели вызывается `restore_state`: активная панель ищется по `persistent_name`, затем применяются `visible` и `zoom`. Для повреждённых элементов есть `InvalidItemView` | Заглушки для отсутствующих плагинов (core §12.6) |
| Автосохранение | Отложенное действие с debounce (`DelayedDebouncedEditAction`) | Debounce сохранения раскладки (core §12.6) |

**Дополнительно:**

| Тема | Решение |
|---|---|
| Каналы с замыканиями (`ExtensionCall`) | Не берём: у нас каналы с данными |
| Рабочая папка плагина через WASI | Не берём: файлы только через `host.vault-*` |
| Кэш предкомпиляции | Берём с оговорками (только собственные артефакты, вне vault) |
| Паника при совпадении `activation_priority` | Не берём: порядок `(priority, plugin_id)` |
| Предварительная проверка плагина (`plugin-verify`) | Своё, аналога в прочитанном коде нет |
| Декларативный UI, модальные окна плагинов | Своё, в расширениях Zed этого нет |

## 7. Лицензии

GPUI распространяется под Apache-2.0, а многие остальные крейты Zed (в том числе `workspace` и `extension_host`), насколько мне известно, под GPL-3.0. Я лицензии не проверял. Перед использованием кода откройте файлы лицензий в нужных крейтах и в репозитории. Безопаснее брать идеи и структуру, а не копировать код: все эскизы в наших документах написаны заново.

## 8. Что проверить в GPUI при реализации

Эскизы в core используют вызовы GPUI. Часть из них я видел в прочитанном коде Zed: `cx.spawn(async move |cx| ...)`, `cx.background_executor().timer(..)`, `cx.defer(..)`, `cx.observe_global_in`, `cx.subscribe_in`, `window.focus(&handle, cx)`, `cx.listener(..)`, `WeakEntity::update`. Остальные (например, `window.focused(cx)` в эскизе модального слоя, core §12.8) нужно сверить с актуальной документацией GPUI.
