# Производительность: таблицы и блоки кода

Дата прогона: ноябрь 2026. Замеры сделаны перед решением, нужны ли отдельные
оптимизации для таблиц и блоков кода. Сырые медианы и массивы замеров лежат в
[`benchmarks/tables-code-blocks-2026-11.json`](benchmarks/tables-code-blocks-2026-11.json).
Пути к APK внутри JSON указывают на временные worktree, которые после замера
удалены; сами результаты и массивы замеров сохранены.

## Итог

Срочных оптимизаций не требуется. Таблицы не дали измеримого прироста,
код и длинные заметки добавляют 2–8 мс, что меньше одного кадра на 60 Гц.
Холодный старт остался в пределах разброса между сборками.

Оптимизации имеют смысл только если появится жалоба на открытие очень больших
заметок на слабом устройстве. В этом случае сначала нужно профилировать
`model_for_editor`, `default_folded_code` и `callout_block_map`, а не менять
layout таблиц.

## Стенд

- Эмулятор `emulator-5554`: Android 16 (API 36), `sdk_gphone64_x86_64`,
  1080×2400, density 420.
- Все сборки — release с R8 и `shrinkResources`.
- Все APK подписаны одним release-ключом, поэтому ставились поверх без очистки
  данных.
- Один и тот же vault и одинаковый набор заметок для всех сборок.
- Тема по умолчанию, без установленных Obsidian-тем.
- У прошлых коммитов `76463df` и `80372d7` в релизе был выключен R8. Для
  честного сравнения они собраны во временных worktree с теми же настройками
  R8, `shrinkResources` и тем же `proguard-rules.pro`, что и текущая сборка.

## Методика

- **Холодный старт**: `am force-stop`, пауза, затем `am start -W`; берётся
  `TotalTime`. 12 прогонов на сборку.
- **Тёплый старт**: `KEYCODE_HOME`, пауза, затем `am start -W`; 10 прогонов.
- **Переключение на уже открытую вкладку**: открыть список вкладок, тапнуть
  `Tables` или `Code`, замерить время от тапа до первого содержательного кадра.
- **Первое открытие заметки**: закрыть целевую вкладку, открыть explorer,
  тапнуть строку заметки; замер включает чтение файла, разбор markdown и первый
  кадр.
- Время открытия считается по логам приложения: `gutter ... lines=N` отмечает
  смену модели, следующий за ним `nativeSurfaceRender` — кадр с новым текстом.
  У сборки `76463df` такого лога нет, поэтому её первое открытие перемерено по
  первому кадру с реальной работой painter (7 прогонов), а не по пустому
  промежуточному кадру.
- `screenrecord` на этом эмуляторе пишет около 5 fps, поэтому для миллисекундных
  замеров он не использовался.
- На сборку: 6 переключений в каждую сторону и 5 первых открытий каждой заметки.
  Текущая сборка прогнана дважды: 22 холодных старта, 18 тёплых, по 11
  переключений в каждую сторону и по 10 первых открытий.

Все значения ниже — медианы в миллисекундах.

## Почему таблицы почти бесплатны

Layout таблицы строится лениво, только для видимой таблицы:

- `build_table_layout` вызывается в момент отрисовки видимого чанка;
- результат кладётся в `table_layouts` по строке заголовка;
- кэш сбрасывается только при смене ширины контента или шрифта кода;
- таблицы, которые сейчас не видны, не измеряются.

Поэтому наличие 30 таблиц в документе само по себе не увеличивает время
открытия заметки.

## Откуда берутся миллисекунды у кода и длинного текста

При смене заметки `ensure_model` заново строит модель всего документа:

```text
model_for_editor(text)          // полный разбор markdown
table_layouts.clear()
default_folded_code(model)      // полный проход по code-блокам
callout_block_map(model)        // полный проход по callout-блокам
```

`callout_block_map` — самая расточительная часть на заметках без callout:
она клонирует каждую строку `raw` в отдельный `String` и собирает
`Vec<Option<CodeBlockState>>` с клонированием языков. Для 1000–1500 строк это
заметный объём аллокаций, хотя callout-блоков в обычной заметке может не быть
вообще.

При этом стоимость ограничена сверху: `model_for_editor` возвращает пустую
модель для текста длиннее 120 000 символов или 4000 строк, и такая заметка
рисуется как обычный текст без markdown-разметки.

## Возможные оптимизации, если понадобятся

Приоритет — от самого безопасного к самому сложному.

1. **Не строить `callout_block_map`, если в документе нет callouts.**
   Дешёвая проверка наличия `[!` по строкам; для обычных заметок убирает
   клонирование всех строк и построение массива состояний.
2. **Не считать `default_folded_code` в source-режиме.**
   Сворачивание кода используется в reading mode. Перед изменением проверить,
   что `wrap_layout` не использует `code_collapsed` в source.
3. **Кэшировать разобранную модель для уже открытых вкладок.**
   Сейчас каждое переключение между вкладками заново строит модель, хотя текст
   не менялся. Это помогает повторным переключениям, но требует хранения модели
   по path и инвалидации при редактировании — заметно более сложная правка.
4. **Layout таблиц не трогать.** Он уже ленивый и кэшированный; оптимизировать
   там нечего.

Отдельно: при первом открытии заметки в логах виден промежуточный кадр за
10–15 мс до содержательного. Это не регресс от таблиц — такое поведение есть и
в старых сборках. Если когда-нибудь понадобится заметно улучшить воспринимаемое
открытие, начинать стоит с двухфазного обновления editor pipeline, а не с
парсера таблиц.

## Когда возвращаться к этому документу

- Появились жалобы на открытие заметок в 1000+ строк на реальном слабом
  телефоне.
- Время первого открытия такой заметки на целевом устройстве стало заметно
  больше 50 мс.
- Профилирование показало, что `callout_block_map` или `default_folded_code`
  занимают существенную долю времени открытия.

Перед изменениями добавить замеры вокруг трёх функций из раздела выше, чтобы
оптимизировать подтверждённый участок, а не предполагаемый.

## Оговорки

- Абсолютные значения холодного старта в этом прогоне (265–275 мс) нельзя
  сравнивать с прошлым отчётом, где было около 466 мс. Тогда эмулятор работал
  в других условиях, vault был другой, а тема — активной. Внутри этого прогона
  все сборки измерены одинаково, поэтому относительные сравнения корректны.
- Медианы на эмуляторе не заменяют замеры на физическом устройстве.
- Сборка `current` на момент замера включала незакоммиченные изменения таблиц и
  кода поверх `a048fb1`. Если эти изменения будут переписаны, цифры нужно
  перепроверить.
