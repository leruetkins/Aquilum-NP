## Контекст и допущения

Вопросы остались без ответа, поэтому беру безопасные значения по умолчанию (их легко поменять до старта):

- **Варианты шрифтов**: «Моноширинный» и «Системный» (Roboto/Noto Sans). Оба уже загружаются ядром (`Painter::new`, surface.rs:784-793), новых файлов не нужно. Serif и произвольные семейства — отдельный опциональный этап.
- **Текст/код в Markdown**: проза (заголовки, абзацы, списки, цитаты) — текстовым шрифтом; fenced-блоки (```) и inline-код (`code`) — шрифтом кода. В код-файлах (language != "") весь текст — шрифтом кода.
- **По умолчанию оба шрифта — моноширинный**, чтобы текущий вид не менялся.
- Размер шрифта остаётся общим для текста и кода (отдельные размеры — не в этой задаче).
- Markdown-парсер (`markdown.rs`, shared `aquilum-gpui/src/markdown/*`) не меняется.

## Архитектурная основа

1. В `Painter` вводится `#[derive(Clone, Copy, PartialEq, Eq, Hash)] enum Face { Ui, Mono }`; bool `mono` заменяется на `Face` в `font`, `font_for_char`, `font_metrics`, `advance`, `width`, `draw`. Ключи кэшей (`glyphs`, `metrics_cache`) получают `Face` вместо bool — нумерация 0/1 сохраняет текущее поведение.
2. Единый источник ширины символа: `Painter::advance_of(char, px, Face) -> f32`, который повторяет ровно ту логику, что и `draw`: Face::Mono — фиксированная ячейка (эмодзи/CJK — 2 ячейки, zero-width — 0), Face::Ui — измеренная ширина глифа (эмодзи — `px`), таб — ширина пробела. Плюс небольшой кэш `(Face, char, px) -> f32` для ASCII.
3. Геометрия редактора перестаёт умножать «номер ячейки» на `advance`: для каждой видимой строки строится массив пиксельных X-смещений (префиксные суммы `advance_of`, скрытые Markdown-маркеры = 0). В монорежиме значения совпадают с текущими, поэтому Этап A не меняет картинку.

## Этап A — перевод раскладки на пиксельные смещения (без изменения вида)

Файл: `vibecodium-mobile/core/src/surface.rs`.

- A1. `Face` в `Painter` (surface.rs:755-1115): замена bool, ключи кэшей, `advance_of` + кэш ширин.
- A2. `wrap_layout` (1547-1619): вместо `max_cols` и подсчёта ячеек — накопление `advance_of` до `content_width`; логику переноса по последнему пробелу/табу сохранить. Сигнатура получает `&mut Painter` и face строки (пока константа Mono). `WrapLine.advance` перестаёт использоваться в геометрии.
- A3. `draw_editor` (2367-2771): для подготовленной строки строить `x_offsets: Vec<f32>` и использовать в оверлеях (2557-2566), выделении (2587-2599), `segment_x` (2622-2627), каретке/handles (2655-2700).
- A4. `editor_position_at` (3071-3154): попадание по ближайшему `x_offset` вместо ячейки; сохранить пропуск zero-width колонок.
- A5. `editor_selection_handles` (3198-3259): те же offsets **с учётом `hidden`** — попутно исправляет текущее расхождение, где handles считаются без скрытых маркеров.
- A6. `line_cell_offsets` (648-680) перестаёт быть источником геометрии; добавить `line_x_offsets(...)` и юнит-тесты на эквивалентность `= cell * advance` в монорежиме; обновить `test_wrap_layout_emoji_boundary` (4231-4247).
- A7. `editor_scroll_metrics` (2890-2899): второе значение (advance) в Kotlin не используется (там читается только `max_y`), вернуть ширину пробела как представительную.

Приёмка A: `cargo check` для обеих Android-ABI, юнит-тесты; на устройстве — `scripts/test_scroll_jitter.py`, ручная проверка каретки/выделения/handles на строках с эмодзи, CJK, табами и скрытыми маркерами. Скриншоты должны совпасть с текущими.

## Этап B — пропорциональный рендер и правила «текст/код»

- B1. `SurfaceState`: поля `text_face`, `code_face` (по умолчанию `Face::Mono`).
- B2. Определение шрифта строки/символа: код-файл (`language` не пуст, 2371-2376) → `code_face`; Markdown-строки `code`/`code_fence` → `code_face`; `span.kind == "inline_code"` (2515-2533) → `code_face`; остальное → `text_face`. Заголовки сохраняют увеличенный кегль (`heading_font`), но face берут по роли.
- B3. `ensure_wrap` (2311-2347) передаёт в `wrap_layout` кегль строки и per-char face; `draw_editor` строит `faces` рядом с `colors` и режет сегменты по паре `(color, face)` (2603-2621), вместо жёсткого `true` в `painter.draw` (2628-2651).
- B4. Оверлеи, выделение, каретка, handles и хит-тест используют тот же `advance_of` с per-char face, чтобы каретка не разъезжалась с глифами.
- B5. Производительность: раскладка остаётся O(n) и пересчитывается только при правке текста/ширины/шрифта (как сейчас); прокрутка не пересчитывает раскладку, ширины берутся из кэша; на кадр добавляется только проход по видимым строкам.

Приёмка B: юнит-тесты переноса с пропорциональными метриками; на устройстве — смешанные комбинации (текст System / код Mono, оба System), проверка переноса, каретки, выделения, табов, эмодзи, CJK, прокрутки.

## Этап D — опционально

- Serif как третий вариант (`NotoSerif-Regular.ttf`, `NotoSerifStatic-Regular.ttf`, `DroidSerif-Regular.ttf` с откатом на Ui) — расширение `Face` и списка в настройках.
- Произвольные семейства из `/system/etc/fonts.xml` — отдельная, более крупная задача (парсинг конфигурации, загрузка файлов по семейству, различия OEM).

## Риски и меры

- Расхождение каретки/выделения с глифами: единый `advance_of` для раскладки и отрисовки; тесты на эквивалентность монорежима.
- Перенос: раскладка не должна зависеть от позиции курсора, поэтому скрытые маркеры в `wrap_layout` по-прежнему не учитываются (как сейчас); при отрисовке и handles они нулевой ширины.
- Скорость набора в больших файлах: wrap уже пересчитывается целиком на каждую правку; кэш ширин ASCII минимизирует добавку, при необходимости — отдельный шаг «инкрементальный wrap».
- Плавность прокрутки: раскладка кэширована, ширины глифов берутся из существующего кэша; проверка `test_scroll_jitter.py` после каждого этапа.
- Устройства без RobotoMono/NotoSansMono уже сейчас падают на UI-шрифт — поведение сохраняется.

## Порядок выполнения

Этапы идут отдельными коммитами/сборками: A (рефакторинг, внешне ничего не меняется) → B (пропорциональный рендер, без UI) → C (настройки) → D по желанию. Можно остановиться после любого этапа. Сейчас устройство не подключено, поэтому визуальная приёмка потребует сборки APK и прогона на телефоне.
